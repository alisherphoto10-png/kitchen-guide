# Часть 5 — разведка: что ещё есть в iiko API (без реализации)

Это **только разведка**, по аналогии с «Частью 0» — узнать и задокументировать,
что реально отдаёт iiko API на demo-стенде, и в каком виде. **Ничего не
реализовывать по итогам этой части** — решение, что из этого делать,
принимается отдельно, после того как будет понятно, что вообще технически
доступно.

Уже подтверждено и используется (`src/services/iiko.js`): `authenticate`,
`getProducts`, `getAssemblyCharts`, `getMeasureUnits`, `getEmployees`,
`getSchedule`, `getEmployeeRoles`. Ниже — что стоит проверить сверх этого.

Для каждого пункта: проверить, существует ли соответствующий эндпоинт в
classic REST API iiko (`/resto/api/...`), сходить на demo-стенде с уже
рабочими кредами из `.env`, сохранить пример реального ответа (можно
сокращённый, с одним-двумя элементами), отметить формат (JSON/XML — как было
с `getEmployees`/`getSchedule`, у которых он оказался XML, а не JSON).

## Для повара

1. **Группы/категории товаров** (`groups` или аналог) — нужно понять, что за
   способом получить категорию блюда. Это закроет уже известный пробел: сейчас
   при `ttk-import` поле категории не заполняется, потому что для него нужен
   именно этот запрос (см. `REPORT-2026-08-11-real-import.md`, раздел
   «Осознанно НЕ сделано»).
2. **Стоп-лист** — какие товары/блюда сейчас недоступны (закончился
   ингредиент). Проверить, есть ли в classic REST API такое понятие вообще, и
   если да — на уровне ресторана или конкретной точки продаж.
3. **Остатки на складе** по ингредиентам — есть ли отчёт/эндпоинт с текущим
   количеством на складе.
4. **Аллергены/модификаторы** в карточке товара — проверить, ведутся ли они в
   iiko вообще (по крайней мере на демо-стенде), и в каком поле.

## Для администрации кухни

5. **Кассовые смены (открытие/закрытие)** — вероятный кандидат на «факт
   прихода/ухода» сотрудника, который обсуждали отдельно (макет «план vs
   факт»). Проверить: есть ли эндпоинт по кассовым сменам, отдаёт ли он время
   открытия/закрытия и кто именно открыл/закрыл, и это вообще про сотрудника
   или только про кассу/точку продаж как таковую (это разные вещи, важно не
   перепутать).
6. **Себестоимость блюда / отчёт по прайм-косту** — есть ли готовый отчёт, или
   это придётся считать самим по брутто/нетто/% потерь (то, что даёт вариант
   Б).
7. **Списания** — есть ли отчёт по списаниям (порча/недостача).
8. **Отчёты по продажам блюд** — что реально продаётся, за период.

## Что явно НЕ входит в эту часть

- Не реализовывать импорт/эндпоинты под найденное — только разведка и отчёт.
- Не проверять на боевых заведениях — только demo-стенд, как и раньше.
- Табель фактически отработанных часов отдельно от кассовых смен — из списка
  сознательно исключён, пока неизвестно, существует ли это в iiko вообще как
  отдельная сущность; если по пути наткнётесь на что-то похожее — стоит
  упомянуть в отчёте, но специально искать не нужно.

## Отчёт

По каждому из 8 пунктов — коротко: есть / нет / не проверено (и почему), для
«есть» — какой эндпоинт, формат ответа (JSON/XML), пример реального ответа
(сокращённый). Если решите, что на сегодня хватит после части пунктов — так и
напишите, это нормально при задаче такого размера, ровно как и в предыдущих
частях.
