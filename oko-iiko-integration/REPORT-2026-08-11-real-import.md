## Что уже было готово (Phase 1, до этой сессии)

Подтверждено чтением кода и живым запросом через `kitchendesk.chefplan.ru`:

- Таблица `iiko_connections` (`restaurant_id UNIQUE`, `base_url`, `login`,
  `password_encrypted` — AES-256-GCM, `last_test_ok_at`). Пароль никогда не
  отдаётся с бэкенда.
- `src/services/iiko.js` — клиент classic REST API iiko (`/resto/api/...`):
  `authenticate`, `getProducts`, `getAssemblyCharts`, `getMeasureUnits`,
  `getEmployees`, `getSchedule`, `getEmployeeRoles`.
- Оба бага из плана — реально пофикшены:
  - `.env`: `IIKO_PASSWORD="user#test"` — в кавычках, `dotenv` не обрезает по `#`.
  - `pickCurrentChart(charts, asOf)` — берёт карту с самым поздним `dateFrom`
    среди тех, чей `dateTo` ещё не наступил (не "последнюю по списку" и не
    "где `dateFrom` уже наступил" — код именно с этой логикой, с комментарием
    про баг на демо-стенде).
- Эндпоинты `POST/GET/DELETE /api/admin/restaurants/:id/iiko/connection`,
  `POST .../connection/test`, `GET .../ttk-preview`, `GET .../schedule-preview`
  — все superadmin-only. Живьём перепроверено сегодня через публичный домен:
  403 не-суперадмину, 404 на тест пустого подключения, GET подключения без
  пароля работает.
- Чего не было: реального импорта в таблицы `ttk`/`schedules` (только preview)
  и какого-либо фронтенда.

## Что сделано сегодня: реальный импорт (вариант А)

### Backend

Два новых эндпоинта в `src/api/admin.js`, в том же superadmin-only разделе,
что и Phase 1 (полный текущий код раздела — [`backend/admin-iiko-routes.js`](./backend/admin-iiko-routes.js)):

- **`POST /api/admin/restaurants/:id/iiko/ttk-import`** — та же выборка
  актуальных карт, что и в `ttk-preview`, но пишет в `ttk.ingredients` строками
  `"название — вес ед."` (helper `formatIikoAmount`: запятая вместо точки, без
  дописывания незначащих нулей). **Идемпотентно**: ищет существующую строку по
  `(restaurant_id, LOWER(name))` — если есть, обновляет только `ingredients`
  (остальные поля, включая ручные правки category/section/фото, не трогает);
  если нет — создаёт новую. Это осознанно отличается от уже существующего в
  проекте `POST /api/admin/ttk/import` (ручная загрузка xlsx-выгрузки) — тот
  всегда создаёт новые строки и будет дублировать при повторном запуске; для
  живого API-импорта, который явно будут запускать повторно, дублирование
  сочли нежелательным.
- **`POST /api/admin/restaurants/:id/iiko/schedule-import?from=&to=`** — тянет
  смены + сотрудников iiko, сопоставляет сотрудника iiko с пользователем
  KitchenDesk **по имени** (`normalizeName`: trim/lowercase/схлопнуть пробелы)
  — в обеих таблицах нет отдельного поля под iiko-id сотрудника, поэтому
  сопоставление текстовое, без изменения схемы БД и без автосоздания новых
  пользователей. Для каждого совпавшего сотрудника на каждый календарный день
  смены (`datesBetween(dateFrom, dateTo)`, посчитано в UTC по срезу даты, без
  привязки ко времени смены) ставится `is_working=true` тем же upsert-запросом,
  что и у ручной простановки в `POST /api/schedule`. Несопоставленные имена
  возвращаются в ответе (`unmatched: [...]`), а не теряются молча.

**Живая проверка на demo-стенде** (restaurant_id=1, уже настроенное и
протестированное подключение `iiko_connections id=2`):
- `ttk-import`: 1-й запуск → `{created:1, updated:0}`; 2-й запуск сразу следом
  → `{created:0, updated:1}` — дублирования нет, идемпотентность подтверждена.
  Импортированная ТТК (id 1055, «картофель отварной») подтверждена видимой в
  обычном `GET /api/ttk`, которым пользуется кухня — то есть встроилась в
  существующий интерфейс без отдельного экрана, как и требовал вариант А.
- `schedule-import`: нашёл 4 смены у сотрудника iiko «Федя», но 0 совпадений
  (`unmatched: ["Федя"]`) — в KitchenDesk на этом ресторане нет пользователя с
  таким именем. Это не баг, а ожидаемое поведение при разъехавшихся именах —
  ровно то расхождение схем, о котором и предупреждал план.
- Заново перепроверены и все 4 живых момента из Phase 1 (403/404/подключение) —
  без регрессий.

### Frontend

Раньше UI для iiko не было вообще (в `Admin.tsx` встречались упоминания
"iiko" только в старом ручном xlsx-загрузчике ТТК — не связано с этой
интеграцией).

Добавлено в `oko-frontend/src/components/features/SuperAdmin.tsx`
(`RestaurantDetail`, панель суперадмина → карточка ресторана) — компонент
`IikoCard` (полный код — [`frontend/IikoCard.tsx`](./frontend/IikoCard.tsx)):
форма подключения (base_url/login/password), кнопки «Проверить» / «Изменить» /
«Отключить», и после успешного подключения — «Импорт ТТК» / «Импорт графика»
с тост-сводкой результата (создано/обновлено/пропущено, число проставленных
дней, список несопоставленных имён). Плюс новые методы `superadminApi.iiko*`
в `services/api.ts` ([`frontend/api-iiko.ts`](./frontend/api-iiko.ts)).

Собрано (`NEXT_PUBLIC_API_URL=https://kitchendesk.chefplan.ru npm run build`)
и задеплоено в `/home/kitchendesk/frontend` — проверено, что собранные чанки
содержат строку «Импорт ТТК».

## Осознанно НЕ сделано

- **TLS**: `rejectUnauthorized: false` в `src/services/iiko.js` оставлен как
  есть — план сам называл это не блокером для демо, а пунктом на будущее перед
  боевыми заведениями. Не трогали.
- **Категория блюда** при импорте ТТК не заполняется (пустая строка) — для
  этого нужен отдельный запрос за группами товаров в iiko, план его не требовал.
- **Автосоздание пользователей** при несовпадении имени в графике — сознательно
  не делается; несопоставленные сотрудники просто отражаются в ответе.
- **Брутто/нетто/% потерь и время смены/должность** — как и договаривались в
  варианте А, не сохраняются вообще.

## Важно про git на сервере

Ни `/root/kitchendesk/backend`, ни `oko-frontend` по факту не под git-контролем
на сервере (see repo history/notes) — правки делались напрямую в файлах,
задеплоены через build+copy и `pm2 restart kitchendesk`, а не через `git commit`
в каком-то серверном репозитории. Эта папка в `kitchen-guide` — единственное
место, где код/отчёт этой задачи попадает под версионный контроль.
