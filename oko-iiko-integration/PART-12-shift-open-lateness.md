> **Статус: закрыто, решено не делать.** Причина — не техническая, а
> практическая: не все сотрудники открывают смену через приложение
> одинаково (кто-то может не открывать вкладку «Смена» вовремя или
> вообще), значит момент открытия вкладки — ненадёжный сигнал для
> «опоздания», и городить механизм под ненадёжные данные не имеет смысла.
> Решение пользователя, после того как выяснилось, что путь через iiko

Продолжение Части 10 (см. `REPORT-2026-08-17-part10-implemented.md`,
раздел «Отклонение от спецификации») — там подтвердили, что в KitchenDesk
сейчас нет вообще никакого механизма, фиксирующего момент, когда
сотрудник реально начал смену. Без этого «опоздание» показывать нечего.

Пользователь попросил проверить путь **через интеграцию с iiko**
(«когда пользователь открыл смену» — взять этот момент из самой iiko, а
не изобретать отдельный механизм в KitchenDesk). Ниже — разведка, почему
этот путь на практике не подходит, и с чем остаёмся.

## Разведка: «открытие личной смены» в iiko — это не то, чем кажется

В iiko действительно есть понятие «личная смена сотрудника»
(`OpenPersonalSession`/`ClosePersonalSession`), но это часть **iikoFront
API** — API кассового терминала (POS), а не classic REST API
(`/resto/api/...`), которым сейчас пользуется вся интеграция KitchenDesk.
Ключевые отличия, из-за которых это не подходит:

1. **Не HTTP-эндпоинт, а плагин.** iikoFront API — это .NET-плагин,
   который должен физически работать **внутри iikoFront на самом
   кассовом терминале** (`PluginContext.Operations`), не удалённый вызов
   с бэкенда KitchenDesk. Штатный сценарий использования (по документации
   iiko) — турникет/терминал учёта рабочего времени: сотрудник
   авторизуется на терминале, плагин на терминале дёргает
   открытие/закрытие личной смены. Наш бэкенд физически не может дёрнуть
   этот метод удалённо HTTP-запросом, как остальные iiko-интеграции в
   этом проекте.
2. **Требует PIN-код сотрудника на терминале** — то есть привязано к
   реальному присутствию человека у кассы/терминала.
3. **Скорее всего вообще не применимо к поварам.** «Личная смена» в iiko
   — это концепция кассы/зала (официанты, кассиры), у которых есть повод
   авторизоваться на терминале. Повара в большинстве заведений с кассой
   вообще не взаимодействуют — то есть даже если бы интеграция была
   технически возможна, для поваров там, скорее всего, просто не будет
   данных.
4. **Соседнее понятие — «кассовая смена» (`OpenCafeSession`/
   `CloseCafeSession`)** — это прямо про кассу/финансы, ровно то, что
   сознательно исключили из прав API-пользователя ещё в Части 8
   (`B_VN`+`B_PER`+`B_EN`, специально без кассы/финансов). Идти в эту
   сторону — значило бы противоречить решению, которое держится с самого
   начала проекта.

Отдельно проверил: у iiko есть общий механизм отчётов
(`GET /resto/api/v2/reports/olap`), в источниках мелькает упоминание
данных о посещаемости — **не подтверждено живьём**, что через него можно
вытащить именно момент открытия личной смены конкретного повара, и даже
если можно, это потребует доступа к отчётам (ещё одно право, не факт что
совместимое с «только чтение без кассы»). Не стал тратить время на
дальнейшее гадание без живой проверки — риск повторить историю с `B_EN`
из Части 9, только на этот раз без ясности, что вообще искать.

## Вывод

Интеграция с iiko для фиксации момента открытия смены **не подходит** —
не технически невозможна в принципе, но требует другого класса доступа
(плагин на кассовом терминале, а не HTTP API), скорее всего не имеет
данных для поваров конкретно, и как минимум частично пересекается с
кассовым контуром, который проект сознательно обходит с Части 8.

Значит — возвращаемся к варианту фиксировать открытие смены **на стороне
самого KitchenDesk**, независимо от iiko. Ранее предлагались два пути:

1. Отдельная кнопка «Начать смену» во вкладке «Смена», симметричная уже
   существующей «Завершить смену» — точнее отражает реальный момент, но
   требует от повара осознанного действия.
2. Автоматически, при первом открытии вкладки «Смена» за день — без
   лишних действий от повара, но менее точно (открыл вкладку из
   любопытства ≠ фактически начал работать).

## Решение — не делать

Спросил, какой из двух вариантов (кнопка вручную / автоматически по
первому открытию вкладки) использовать. Ответ пользователя: не все
сотрудники вообще открывают смену через приложение одинаково — то есть
оба варианта опираются на действие, которое часть сотрудников просто не
совершает предсказуемо. Раз источник данных ненадёжен по своей природе
(не техническая недоработка, а факт о том, как люди реально
пользуются приложением), опоздание и время открытия смены **не
реализуем** — ни через iiko, ни своими силами. Вычёркиваем этот пункт из
планов, а не оставляем висеть.
