# OKO ↔ iiko — план интеграции (инструкция для сессии на сервере)

Это временная папка-склад в репозитории `kitchen-guide`, по аналогии с
`oko-order-relay/` — сюда положен не код, а **письменный план и решения**,
которые обсуждались в чате, но реализовывались напрямую на сервере (не в
git). У меня (сессия Claude Code on the web) нет доступа к тому серверу и
нет самого кода — поэтому ниже пересказ того, что было решено и найдено, а
не проверенная реализация. Открой эту ветку в той сессии, где есть доступ к
серверу, и используй файл как ТЗ/чеклист, сверяясь с реальным кодом на месте.

Ветка: `claude/oko-iiko-integration`. После деплоя эту папку из репозитория
можно удалить (как и `oko-order-relay/`).

## Контекст задачи

Кухонный интерфейс (KitchenDesk, часть проекта OKO) нужно связать с iiko —
забирать оттуда:
1. **ТТК** (технико-технологические карты, составы блюд);
2. **График** смен поваров.

и показывать это в KitchenDesk.

## Что уже решено по архитектуре подключения к iiko

- Подключение к iiko хранится **на заведение** в отдельной таблице
  `connections` (или аналогичной) — у каждого заведения свои креды/URL стенда.
- Управлять подключениями (создавать/тестировать/удалять) может **только
  суперадмин** — обычный админ должен получать `403`.
- Удаление подключения — обычный CRUD, должно быть покрыто тестом.
- Повторный тест **пустого** (ещё не настроенного) подключения должен
  возвращать `404`, а не 200/500.
- Эти четыре момента (403 не-суперадмину, успешное удаление, 404 на пустое
  подключение, плюс базовый happy-path подключения) были проверены вживую на
  демо-стенде iiko и работали корректно на момент разговора — но раз кода в
  git нет, это нужно перепроверить по факту на сервере, а не считать
  доказанным.

## Два бага, которые всплыли по пути (обязательно проверить, что учтены)

### 1. `dotenv` обрезает значения по `#`
Если пароль/значение переменной в `.env` содержит `#` и не взято в кавычки,
`dotenv` интерпретирует всё после `#` как комментарий и тихо обрезает
значение. Пример: `IIKO_PASSWORD=user#test` превращается в `user`, и
авторизация к iiko будет молча падать без явной ошибки о неверном пароле.

**Фикс:** все значения в `.env`, где потенциально может быть `#` (пароли,
токены), брать в кавычки: `IIKO_PASSWORD="user#test"`.

Проверить на сервере: действительно ли `.env` с iiko-кредами использует
кавычки для таких значений.

### 2. Выбор «актуальной» версии ТТК
У блюда в iiko может быть несколько версий ТТК с разными периодами действия
(`dateFrom`/`dateTo`). Наивный выбор «последней в списке» брал не ту карту
из-за рассинхрона времени на демо-стенде (та же природа проблемы, что
раньше была с накладными).

**Правильная логика:** брать карту с **самым поздним `dateFrom`, у которой
`dateTo` ещё не наступил** (то есть действующую прямо сейчас, а не просто
«последнюю созданную»).

Проверить на сервере: используется ли именно эта логика при импорте ТТК.

## Риск, отмеченный на будущее (не блокер для демо, но важно)

Запросы к iiko-стенду сейчас идут с отключённой проверкой TLS-сертификата
(`rejectUnauthorized: false`) — демо-стенд не проходит валидацию сертификата
штатным способом. Для теста это ок, но **перед подключением реальных
(боевых) заведений это нужно пересмотреть** — иначе трафик к iiko не
защищён от подмены (MITM).

Отметка для сервера: не забыть вернуть/настроить нормальную проверку TLS
перед продакшен-подключением реальных заведений, либо явно задокументировать
исключение (например, pinning сертификата демо/тестового стенда отдельно от
боевого).

## Несовпадение схем данных (OKO vs iiko)

Наша схема ТТК/графика заметно проще, чем у iiko:

| | OKO (сейчас) | iiko |
|---|---|---|
| ТТК: состав | `ingredients` — свободный текст, например `«ПФ Бок Чой кимчи — 0,060 кг»` | брутто/нетто/% потерь по каждому ингредиенту, структурированно |
| График | булево `is_working` на день (работал/не работал) | смены со временем начала/конца и должностью |

Прямого совпадения полей нет, поэтому выбирали между двумя путями.

## Принятое решение: Вариант А (быстрый импорт как текст)

Договорились делать **вариант А** — без изменения схемы БД:

- **ТТК:** состав ингредиентов из iiko сериализовать в ту же текстовую
  строку, что и сейчас в `ingredients` (`"название — вес"`), просто собирая
  её из данных iiko вместо ручного ввода. Брутто/нетто/% потерь **не**
  сохраняем отдельно — теряется точность, но не ломается существующий UI.
- **График:** для каждого дня, где в iiko есть смена у сотрудника, ставим
  `is_working = true` в нашей таблице; время начала/конца и должность **не**
  переносим.
- Ничего не ломает в существующем интерфейсе KitchenDesk — можно быстро
  показать, что данные реально приходят из iiko.
- Явный компромисс: нельзя будет автоматически считать себестоимость по
  граммовкам (для этого нужен вариант Б — структурные поля брутто/нетто/%
  потерь и время+должность в графике). Вариант Б сознательно отложен на
  потом, если понадобится точность — отдельная, более крупная задача, т.к.
  трогает все места, где эти таблицы уже используются (экспорт, отображение
  и т.д.).
