# Инструкция для технолога — отдельный API-пользователь iiko для KitchenDesk

Для кого: технолог/администратор заведения, который настраивает
подключение к iiko в KitchenDesk. Не нужно отдавать KitchenDesk личный
административный логин/пароль от iiko — заведите отдельного сотрудника
специально под интеграцию, с правами только на чтение того, что нужно
(товары, ТТК, сотрудники, график), без доступа к кассе/финансам/
списаниям. Ниже — точные шаги и права, подтверждённые живой проверкой
(Части 8–9 в этом репозитории), не предположение из документации iiko.

## 1. Создать сотрудника в iiko

В iiko (iikoOffice/iikoWeb): **Сотрудники → Сотрудники → Добавить**.

- Имя — любое понятное, например `API KitchenDesk`.
- Логин/пароль — придумать отдельные, не переиспользовать ничьи личные.
  Именно их вводить потом в форму подключения KitchenDesk.
- Пинкод — можно оставить пустым/дефолтным, KitchenDesk его не использует.

## 2. Создать или назначить урезанную должность

**Сотрудники → Роли** → создать новую роль (например,
`API-интеграция`) или использовать существующую урезанную, если уже
заводили. Назначить эту роль сотруднику из шага 1.

## 3. Права доступа — точный набор

Открыть права доступа этой роли, развернуть дерево прав целиком и
включить **ровно три** права (без кассы, без финансов, без списаний):

| Код | Название в дереве прав | Зачем |
|---|---|---|
| `B_VN` | Просмотр номенклатуры | Список товаров/блюд для импорта ТТК |
| `B_PER` | Просмотр личных данных сотрудников | Список сотрудников для сопоставления в графике |
| `B_EN` | Редактирование номенклатурных справочников | Без него `403 Permission denied: B_EN...` — нужен именно для запроса, которым KitchenDesk тянет данные графика/справочников (подтверждено живьём, см. `REPORT-2026-08-15-part9-live-restricted-user.md`) |

Почему `B_EN` («редактирование», а не «просмотр») — да, звучит нелогично
для интеграции, которая должна только читать данные, но это подтверждённый
на практике факт, не предположение: без него `getEmployeeRoles`/
`getMeasureUnits` отдают `403`, с ним всё, включая реальный «Импорт ТТК» и
«Импорт графика», проходит без ошибок.

**Не включать ничего сверх этих трёх** — если в дереве прав рядом есть
похожие пункты «на всякий случай», их включать не нужно: должность должна
оставаться максимально урезанной.

Сохранить роль.

## 4. Подключить в KitchenDesk

Карточка ресторана → блок «Подключение к iiko» → кнопка «Изменить» (или
заполнить с нуля, если подключения ещё нет):

- **URL** — адрес стенда iiko этого заведения (тот же, что используется
  для входа в iikoOffice/iikoWeb).
- **Логин/пароль** — те, что создали в шаге 1.

Нажать **«Проверить»**.

## 5. Проверка после подключения

Пройти по списку, каждый пункт должен отработать без ошибок:

1. **«Проверить»** в форме подключения → `{"ok": true}`.
2. **«Импорт ТТК»** → тост с результатом (создано/обновлено/пропущено),
   без ошибки прав.
3. **«Импорт графика»** → тост с результатом (число проставленных дней,
   список несопоставленных имён, если есть), без ошибки прав.

Если на любом из пунктов всплывает `403 Permission denied: <код>` —
значит для конкретно этого заведения (другая версия iiko, другие
настройки) нужно ещё одно право сверх трёх из шага 3. Порядок действий:
открыть дерево прав этой роли, найти строку с этим кодом (рядом всегда
человекочитаемое название), включить **только её**, повторить проверку.
Не включать права охапкой «на всякий случай» — по одному, с перепроверкой
после каждого.

## Про лицензию

При создании такого сотрудника отдельно понаблюдать (в самой iiko, при
создании) — не появляется ли предупреждение о лимите пользователей/
лицензии. На demo-стенде при проверке (Часть 9) ничего тревожного не
всплыло, но это не гарантирует то же самое на всех тарифах iiko — если на
конкретном заведении лимит есть, потребуется либо освободить слот, либо
уточнить у iiko, считается ли API-пользователь отдельным слотом на их
тарифе.
