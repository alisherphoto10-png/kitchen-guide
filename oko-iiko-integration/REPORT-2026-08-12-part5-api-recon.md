# Отчёт — Часть 5: разведка classic REST API iiko (demo-стенд)

Только разведка, как и было заказано в `PART-5-api-recon.md`. Ничего не
реализовано и не задеплоено по итогам. Проверено вживую на demo-стенде
(`IIKO_BASE_URL` из `.env` бэкенда, `542-903-605.iiko.it/resto`), теми же
кредами, что использует `src/services/iiko.js`. Ходил напрямую `https` (без
изменений в коде), логинился через `/api/auth`, в конце каждой сессии —
`/api/logout`. У демо-стенда в номенклатуре всего 5 товаров (2 служебных
округления, картофель, лук репчатый, картофель отварной) и 1 группа — это
ограничивает то, что можно увидеть "живым" примером, но не ограничивает
проверку самого факта наличия эндпоинта/поля.

Итог по восьми пунктам — 6 «есть», 1 «нет (не найдено)», 1 «есть, но нет
данных для примера» (пункт 8, отчасти и 5, 6, 7 — см. ниже, у них тоже пустые
данные, но сами механизмы подтверждены).

## Для повара

### 1. Группы/категории товаров — ЕСТЬ

- **Эндпоинт:** `GET /resto/api/v2/entities/products/group/list?key=<token>`
- **Формат:** JSON
- Товар ссылается на группу через своё поле `parent` (у товара, из
  `/api/v2/entities/products/list`) — это тот же id, что `id` группы.
  Проверено: у двух служебных товаров ("Округление в пользу гостя" и
  "Округление цены за единицу в пользу гостя") `parent` реально равен id
  группы "Сервисный сбор". Механизм рабочий.
- **Важная оговорка:** у реальных блюд/товаров демо-стенда (картофель, лук
  репчатый, картофель отварной) `parent` = `null` — на этом демо-стенде у них
  просто не назначена группа в самой iiko. То есть пробел с пустой категорией
  при импорте ТТК (см. `REPORT-2026-08-11-real-import.md`) технически
  закрывается этим эндпоинтом (нужно всего лишь резолвить `product.parent` →
  `group.name`), но подтвердить это на реальном заполненном примере блюда с
  группой на этом демо-стенде не вышло — там просто нет блюд с назначенной
  группой. Стоит перепроверить на заведении, где группы у блюд реально
  расставлены.
- **Пример ответа** (единственная группа на демо, сокращённо):
  ```json
  [{
    "id": "7bce50f2-c5d0-1bb7-5194-8d2e55752764",
    "deleted": false,
    "name": "Сервисный сбор",
    "parent": null,
    "modifiers": [],
    "category": null,
    "accountingCategory": null
  }]
  ```

### 2. Стоп-лист — НЕ НАЙДЕНО

- Проверены запросы:
  - `GET /api/v2/entities/list?rootType=StopList` → `409 Following types are
    not supported: [StopList]`
  - то же самое с `rootType=StopListItem`, `OutOfStockItem`,
    `StopListEntry`, `ProductStopList` — все `409`, тем же способом.
  - `GET /api/v2/entities/stoplist` → `404`
  - `GET /api/v2/stopLists` → `404`
  - `GET /api/v2/entities/products/stopSKU` → `404`
- Для контроля: `rootType=MeasureUnit` (уже рабочий, используется в
  `iiko.js`) в той же сессии вернул `200` — значит сам механизм
  `entities/list` жив, просто среди поддерживаемых `rootType` стоп-листа нет.
- **Вывод:** в classic REST API (`/resto/api/...`) на этой версии demo-стенда
  прямого эндпоинта для стоп-листа не нашёл ни по одному из опробованных
  путей. Судя по всему (по открытым обсуждениям iiko-разработчиков), стоп-лист
  — это в первую очередь сущность iikoFront (кассового терминала), а не
  серверного classic REST API; официальную документацию classic REST API с
  публичным списком всех эндпоинтов найти не удалось, чтобы подтвердить это
  окончательно на 100% — помечаю как «не найдено», а не жёсткое «нет».

### 3. Остатки на складе — ЕСТЬ

- **Эндпоинт:** `GET /resto/api/v2/reports/balance/stores?key=<token>&timestamp=<ISO datetime>`
- **Формат:** JSON
- Отдаёт плоский список `{store, product, amount, sum}` — `store` и
  `product` это id (нужно резолвить через `entities/list?rootType=Store` и
  `products/list`).
- **Пример реального ответа** (демо-стенд, полностью, без сокращений — там
  всего 2 позиции):
  ```json
  [
    {"store": "1239d270-1bbe-f64f-b7ea-5f00518ef508", "product": "6f4e9bde-dc46-4a00-a878-378e37882b8d", "amount": 5, "sum": 25000},
    {"store": "1239d270-1bbe-f64f-b7ea-5f00518ef508", "product": "ba32614c-ce7d-47e1-ac0e-37344b6cf280", "amount": 10, "sum": 100000}
  ]
  ```
  (`sum` — видимо в копейках/сотых, как и цены в `products/list`.)
- Примечание из внешней документации (не подтверждено на этом демо
  напрямую, но стоит иметь в виду): `timestamp` рекомендуют брать после
  23:00, чтобы попал автоматический акт сверки за день.

### 4. Аллергены/модификаторы — ЕСТЬ ПОЛЕ, но не проверено с реальными данными

- Поле есть прямо в карточке товара из уже используемого
  `GET /resto/api/v2/entities/products/list?key=<token>` (JSON, тот же
  эндпоинт, что уже используется в `iiko.js`) — отдельный эндпоинт не нужен:
  - `allergenGroups` — на всех 5 товарах демо-стенда стоит `null`.
  - `modifiers` — на всех 5 товарах демо-стенда `[]` (пустой массив).
- **Вывод:** поле в схеме объекта товара присутствует, значит classic API
  умеет отдавать аллергены/модификаторы как минимум по контракту, но на этом
  демо-стенде ни у одного товара они не заполнены — реального непустого
  примера получить не удалось. Нужно либо завести аллергены/модификаторы на
  демо-товаре и проверить снова, либо смотреть на боевом заведении (что вне
  рамок этой части).
- **Пример** (фрагмент карточки товара, как есть):
  ```json
  {
    "name": "картофель отварной",
    "type": "DISH",
    "modifiers": [],
    "allergenGroups": null,
    "coldLossPercent": 5,
    "hotLossPercent": 36
  }
  ```
  (Кстати, заодно видно: в карточке товара уже реально лежат
  `coldLossPercent`/`hotLossPercent` — это те самые % потерь для варианта Б,
  на будущее.)

## Для администрации кухни

### 5. Кассовые смены (открытие/закрытие) — ЕСТЬ ЭНДПОИНТ, данных на демо нет

- **Эндпоинт:** `GET /resto/api/v2/cashshifts/list?key=<token>&status=ANY&openDateFrom=yyyy-MM-dd&openDateTo=yyyy-MM-dd`
- **Формат:** JSON
- Даты обязательно в формате `yyyy-MM-dd` (без времени) — при попытке
  передать `2024-01-01T00:00:00` получил явную ошибку валидации:
  `409 Неверная дата 2024-01-01T00:00:00. Введите дату в формате 'yyyy-MM-dd'.`
  С датой в правильном формате (`openDateFrom=2026-01-01&openDateTo=2026-12-31`)
  — `200`, тело `[]`.
- **Вывод:** эндпоинт существует и реально отвечает `200`, но на demo-стенде
  ни одной кассовой смены не зафиксировано (ни одна касса не
  открывалась/закрывалась) — значит нельзя увидеть реальный пример полей
  (кто открыл/закрыл, время) и тем более нельзя пока подтвердить или
  опровергнуть саму гипотезу «кассовая смена = факт прихода/ухода
  сотрудника» (или это только про кассу/точку продаж, а не конкретного
  человека) — для этого нужно либо открыть/закрыть смену на демо вручную
  (через iikoFront/веб), либо смотреть на боевом заведении, где кассы
  реально работают. Пункт технически не закрыт до конца — эндпоинт есть,
  содержательный ответ по нему не проверен.

### 6. Себестоимость блюда / прайм-кост — ЕСТЬ, данных на демо нет

- **Эндпоинт:** `POST /resto/api/v2/reports/olap?key=<token>` (тот самый
  OLAP-конструктор отчётов, `reportType: "SALES"`).
- **Формат:** JSON (запрос и ответ)
- У отчёта `SALES` есть отдельная группа полей с тегом `"Себестоимость"`
  (список полей получен через `GET /resto/api/v2/reports/olap/columns?reportType=SALES&key=<token>` — тоже JSON, отдаёт справочник всех допустимых
  полей отчёта с флагами `aggregationAllowed`/`groupingAllowed`/`filteringAllowed`):
  - `ProductCostBase.ProductCost` — «Себестоимость» (MONEY)
  - `ProductCostBase.OneItem` — «Себестоимость единицы»
  - `ProductCostBase.Percent` / `ProductCostBase.PercentWithoutVAT` — «Себестоимость(%)» — это и есть food cost %, готовый прайм-кост без ручного счёта по брутто/нетто/%потерь
  - `ProductCostBase.Profit` / `ProductCostBase.MarkUp` — наценка
- Поле `OpenDate.Typed` (учётный день) — **обязательный** фильтр для
  `SALES`-отчёта, без него `409`: `OLAP-запрос отклонен, поскольку в запросе
  не найден ни один из необходимых фильтров: Учетный день (OpenDate.Typed)`.
- Запрос с полем `ProductCostBase.ProductCost` прошёл (`200`), но данные
  пустые — `{"data":[],"summary":[]}` — потому что на демо-стенде за весь
  проверенный период (2020–2026) в этом ресторане нет ни одной продажи (см.
  пункт 8, там та же причина). Другие правдоподобные названия полей
  (`Cost`, `CostPrice`, `DishCostInt`, `FoodCostSum`, `FoodCostPercent`) —
  все отклонены как `Unknown OLAP field`, реальное имя именно
  `ProductCostBase.*`.
- **Вывод:** есть готовый отчёт (не нужно считать самим по брутто/нетто/%
  потерь) — это вариант «А+»: точную себестоимость и % можно получить прямо
  из iiko через OLAP, если там реально фиксируются продажи. На этом
  демо-стенде продаж нет, поэтому живого ненулевого примера значений
  получить не удалось.
- **Пример запроса** (рабочий, просто с пустым результатом):
  ```json
  POST /resto/api/v2/reports/olap?key=<token>
  {
    "reportType": "SALES",
    "buildSummary": true,
    "groupByRowFields": ["DishName"],
    "aggregateFields": ["DishAmountInt", "DishSumInt", "ProductCostBase.ProductCost"],
    "filters": { "OpenDate.Typed": { "filterType": "DateRange", "periodType": "CUSTOM", "from": "2020-01-01", "to": "2026-12-31" } }
  }
  → 200 {"data":[],"summary":[]}
  ```

### 7. Списания — ЕСТЬ МЕХАНИЗМ, пример без реального списания

- Отдельного `/documents/writeoff/...` эндпоинта не нашёл (проверил
  `GET /api/v2/documents/writeoff/list` → `404`,
  `GET /api/documents/export/writeoffDocument` → `404`).
- Но списания доступны через тот же OLAP-конструктор:
  **`POST /resto/api/v2/reports/olap?key=<token>`, `reportType: "TRANSACTIONS"`**
  (JSON). У этого отчёта есть группируемое/фильтруемое поле `TransactionType`
  (ENUM, «Тип транзакции») — по документации и по факту работы это тип
  складской проводки (приход/расход/списание и т.п.); списание, по всей
  видимости, отдельное значение этого enum (кандидат — что-то вроде
  `WRITEOFF`, но на демо ни одного такого значения не встретилось — см.
  ниже).
- **Реальный (непустой!) пример с демо-стенда** — сгруппировано по товару и
  типу транзакции, агрегаты `Amount` (количество) и `Sum.ResignedSum`
  (сумма):
  ```json
  POST /resto/api/v2/reports/olap?key=<token>
  {
    "reportType": "TRANSACTIONS",
    "groupByRowFields": ["TransactionType", "Product.Name"],
    "aggregateFields": ["Amount", "Sum.ResignedSum"],
    "filters": {"DateTime.Typed": {"filterType": "DateRange", "periodType": "CUSTOM", "from": "2020-01-01", "to": "2026-12-31"}}
  }
  → 200
  {"data":[
    {"Amount":10,"Product.Name":"Картофель","Sum.ResignedSum":0,"TransactionType":"INVOICE"},
    {"Amount":5,"Product.Name":"лук репчатый","Sum.ResignedSum":0,"TransactionType":"INVOICE"}
  ], "summary":[...]}
  ```
- **Вывод:** на демо-стенде вообще есть только один вид складских проводок —
  `INVOICE` (это приходная накладная, ей и приходовали картофель/лук). Ни
  одного списания за всё время на этом заведении не заводили, поэтому
  подтвердить конкретное имя enum-значения для списания и увидеть его в
  реальном ответе не вышло — сам факт, что отчёт по транзакциям с фильтром
  по типу работает и отдаёт JSON, подтверждён; конкретно «списание»
  предстоит подтвердить либо заведя тестовое списание на демо, либо на
  заведении, где списания реально бывают.

### 8. Отчёты по продажам блюд — ЕСТЬ ЭНДПОИНТ, данных на демо нет

- **Эндпоинт:** `POST /resto/api/v2/reports/olap?key=<token>`, `reportType: "SALES"` — тот же самый OLAP-конструктор, что и для себестоимости (пункт 6),
  просто с другим набором полей.
- **Формат:** JSON
- Поля учтены/проверены: `DishName`, `DishAmountInt` (кол-во),
  `DishSumInt` (сумма), `DishDiscountSumInt` (сумма скидки) — все приняты
  (`200`), но с пустым результатом.
- Проверил несколько широких периодов (2020–2026, весь диапазон дат демо) —
  везде `{"data":[],"summary":[]}`. Без фильтра по `OpenDate.Typed` совсем —
  сервер жёстко требует этот фильтр (см. пункт 6), так что «отчёт без дат»
  не вариант.
- **Вывод:** эндпоинт и формат подтверждены (правильные поля, правильная
  структура запроса, `200` без ошибок), но реальных продаж на этом
  demo-стенде физически не было зафиксировано ни разу за весь период — это
  согласуется с тем, что там всего 1 приходная накладная и 0 кассовых смен
  (пункт 5). Живой ненулевой пример по продажам получить с этого стенда не
  вышло технически (не из-за API, а из-за отсутствия данных) — нужен
  demo-стенд с хотя бы одной реально проведённой продажей, либо боевое
  заведение.

Общая наблюдение по пунктам 4–8: этот конкретный demo-стенд крайне «пустой»
(5 товаров, 1 группа, 1 накладная, 0 продаж, 0 кассовых смен, 0 списаний) —
он подтверждает *механизм и формат* API, но не может подтвердить *реальные,
непустые* данные там, где их на нём просто никогда не было. Это стоит иметь
в виду при принятии решения, что делать дальше: возможно понадобится либо
завести на демо тестовые операции (продажу, смену, списание), либо
проверить то же самое на подключённом боевом заведении (с учётом, что это
уже другой уровень риска, чем демо).

Решение, что из этого списка реализовывать (и в каком порядке), принимается
отдельно — как и договаривались, эта часть только разведка.
