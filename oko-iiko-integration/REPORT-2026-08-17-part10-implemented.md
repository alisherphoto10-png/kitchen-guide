# Отчёт — Часть 10 реализована и задеплоена

Реализацию делала сессия с доступом к серверу (по формулировке задачи из
`PART-10-employee-schedule-visibility.md`). Ниже — что она сообщила по
факту, сверено с планом.

## Бэкенд (`/root/kitchendesk/backend`, задеплоено, `pm2 restart kitchendesk`)

- `schedule-import` теперь пишет время смены и роль **рядом** с
  `is_working` (аддитивно, как и требовалось — существующая логика не
  тронута). Роль резолвится через `iiko.getEmployeeRoles`, с fallback на
  пустой список, чтобы отсутствие ролей не ломало сам импорт.
- `GET /api/schedule/today` и `GET /api/schedule/colleagues?date=` — оба
  живьём проверены `curl`'ом с реальным JWT на demo-стенде
  (`restaurant_id=1`): пустое состояние без импорта, полное состояние
  после тестовой вставки. **Явно подтверждено — роль/грейд нигде не
  отдаётся** (ключевое требование по зарплатной чувствительности этой
  метки, см. Часть 10). Тестовые строки после проверки удалены из БД.

## Фронтенд (собран и задеплоен через `rsync --delete`, с сохранением
`oko-order`/логотипа — то есть без случайного затирания соседних частей
статики)

- `Dashboard.tsx` — карточка своей смены под бейджами в шапке
  приветствия, три состояния (заглушка / выходной / время), тап
  открывает шторку с неделей.
- `Profile.tsx` — блок «Коллеги по цеху сегодня» рядом с карточкой
  «Информация».

Совпадает с решениями из Части 10: разделение экранов, тап-раскрытие
недели, заглушка на время до готовности данных, скрытие роли/грейда.

## Отклонение от спецификации — опоздание и время открытия смены

**Не реализовано.** Причина подтверждена явно (не предположение) —
в боевом коде сейчас физически нет механизма, который фиксирует момент
фактического открытия смены с timestamp'ом. Часть 10 прямо предупреждала
не изобретать это на ходу, если такого механизма нет — реализующая сессия
поступила по инструкции: проверила и, не найдя, честно отложила пункт,
а не подделала расчёт на пустом месте.

**Следствие**: показ опоздания на «Главной» — отдельная, самостоятельная
задача (условно, «Часть 12»): сначала добавить фиксацию времени открытия
смены в механизм вкладки «Смена» (само по себе может быть полезно и без
привязки к опозданиям — учёт фактического начала работы), и только потом
возвращаться к вычислению и показу опоздания. Не начинать эту задачу
между делом — она меняет поведение существующей вкладки «Смена», заслуживает
собственного рассмотрения (в частности, нужно решить, что считается
«опозданием», если сотрудник открывает смену раньше или самого приложения
ещё не открывал вовремя).
