# OKO Waiter Guide — инструкция по деплою

Пособие для официантов: разделы меню → блюда, у каждого блюда —
описание, история, «как подать гостю», калькуляция (одна или несколько
таблиц ингредиентов) и фото. Редактируется через админку (пароль), читают
официанты через отдельную страницу без пароля — по образцу
`oko-order-relay` (форма заказа тоже без пароля, просто непубличная
ссылка).

Это временная папка-склад в репозитории `kitchen-guide` — код попал сюда
только для передачи на сервер, как `oko-order-relay/` и `oko-inventory/`.
После деплоя можно удалить.

## Структура

```
backend/
  oko-waiter-guide-api.js       — Express-роутер: /guide и /photos (публичные),
                                    /admin/* (за X-Admin-Password)
  oko-waiter-guide-store.js     — файловое хранилище (JSON): sections.json, dishes.json, photos/
  oko-waiter-guide-md-import.js — разбор .md-файла с блюдами для массового импорта
                                    (см. «Импорт из файла» ниже)
frontend/
  admin/index.html               — редактор (разделы, блюда, калькуляция, фото,
                                     импорт из файла)
  guide/index.html                — то, что открывают официанты — без пароля
```

## Как это устроено

**Разделы и блюда — раздельные сущности.** У блюда есть `sectionId`.
Если раздел удаляют, блюда не исчезают — попадают в «Без раздела» (видно
и в админке, и через `GET /admin/orphan-dishes`) — их можно переназначить
в другой раздел или удалить вручную.

**Калькуляция — массив таблиц**, не одна плоская таблица. У составных
блюд (как «Тар тар» — основа + гарнир отдельно) может быть несколько
таблиц, каждая со своей необязательной подписью и списком ингредиентов
(название / ед. изм. / количество). Формат подобран специально под
структуру присланного файла-пособия, где у части блюд ровно так и было —
две таблицы на одно блюдо.

**Фото — свои, не связаны с ТТК.** Каждое блюдо может получить своё
фото через админку (как в `oko-inventory`) — независимо от карточек ТТК
в самом KitchenDesk. Решение осознанное: ТТК и это пособие — разные
системы, автоматическая связка по названию была бы хрупкой (совпадение
имён не гарантировано). Хранятся отдельными файлами, раздаются через
`GET /photos/:filename` — без пароля (это open-режим страницы для
официантов, официанты не должны логиниться, чтобы посмотреть фото блюда).

**Публичная страница `/guide`** (и одноимённый API-роут) — без пароля,
специально: официанты открывают по прямой ссылке с телефона, не вводя
ничего. Как и форма заказа в `oko-order-relay`, ссылка не публикуется
широко, но технически не защищена — для справочного материала (не
персональных/финансовых данных) это соразмерно. Авторизацию по ТЗ
сознательно не добавляли — второй раз изобретать логин поверх уже
принятого решения смысла не было.

## Публичная страница — по ТЗ «точь-в-точь»

Страница официанта (`frontend/guide/index.html`) переписана под макет
и ТЗ: главный экран (поиск + категории, живой фильтр с debounce ~250мс),
отдельный экран списка блюд на категорию (или «Все блюда» — включает
поиск по названию/описанию/разделу/ингредиентам сразу), страница блюда
с вкладками **Состав / История / Подача / Важно**, каруселью фото (свайп +
счётчик «1/3»), избранным (♡, только на этом устройстве — в localStorage,
не синхронизируется между официантами) и FAQ-аккордеоном.

**У каждого блюда и раздела свой URL**, набираемый прямо в адресной
строке и переживающий обновление страницы:
- `/waiter-guide/category/holodnye-zakuski`
- `/waiter-guide/dish/tar-tar`

Слаг (`tar-tar`) считается на лету из названия при каждом запросе — не
хранится в файле, поэтому не может «протухнуть» отдельно от данных.
Переименовали блюдо — слаг в тот же момент пересчитался везде разом.
Требует правки nginx, см. «Шаги деплоя» ниже.

**Новые поля блюда** (необязательные — старые блюда без них отображаются
корректно, просто без вкладки/раздела, который бы использовал именно
это поле):
- `status` — `hit` (🔥 Хит) или `popular` (🌟 Популярное), бейдж в списке и на странице блюда;
- `photos` — массив (не одно фото) — можно добавить несколько, свайпаются на странице блюда;
- `historyQuote` — цитата-факт отдельной карточкой во вкладке «История»;
- `servingSteps` — список шагов подачи (✓ built, вкладка «Подача»);
- `waiterPhrase` — то, что раньше называлось «как подать гостю» (данные не потерялись,
  просто переименовано под смысл ТЗ — «что сказать гостю»);
- `allergens` / `features` / `recommendations` — три отдельных списка на вкладке «Важно»
  (красный/синий/зелёный значок соответственно);
- `faq` — вопрос/ответ, аккордеон внизу вкладки «Важно»;
- `hidden` — скрыть блюдо со страницы официанта, не удаляя его из редактора.

Разделы получили `icon` — ключевое слово из фиксированного набора
(`cutlery`, `salad`, `hot`, `soup`, `meat`, `pasta`, `pizza`, `skewer`,
`sushi`, `bread`, `dessert`, `drink`, `beer`, `sauce`) — набор иконок
общий у админки (выбор в форме раздела) и у публичной страницы (сама
иконка).

**Подразделы — один уровень вложенности.** У раздела появилось `parentId` —
раздел может содержать подразделы (например «Холодные закуски» →
«Севиче» / «Тартары»), но у подраздела своих подразделов быть не может
(два уровня, не дерево произвольной глубины). Блюдо можно завести и прямо
в раздел с подразделами (просто не попадёт ни в один из них), и в сам
подраздел — оба варианта равноправны. На главном экране в чипсах —
только разделы верхнего уровня; открыв раздел с подразделами, под
поиском появляется ещё одна строка чипсов («Раздел — всё» / каждый
подраздел), фильтр синхронизирован с URL (`?sub=slug`), переживает
обновление страницы. У подраздела тоже свой URL
(`/waiter-guide/category/seviche`), как и у обычного раздела.

**Статусы блюд («🔥 Хит» и т.п.) — управляемый список, не два жёстко
зашитых варианта.** Отдельная сущность (`data/statuses.json`), CRUD через
новую карточку «Статусы блюд» в админке (создать/переименовать/сменить
эмодзи/удалить). При удалении статуса блюда с ним не портятся — статус
просто снимается. По умолчанию (при первом обращении) заводятся те же
два, что были раньше (`hit`/`popular` с этими же id) — старые блюда
находят свой статус без миграции.

**Обратная совместимость без миграции.** Старое поле `photo` (одно фото)
и `howToServe` по-прежнему читаются, если новых `photos`/`waiterPhrase` ещё
нет — ни один из уже занесённых 72+26 блюд не потерял данные, просто
хранилище на лету понимает оба варианта.

**Фон главного экрана — пока не фото.** В макете за поиском — атмосферное
фото; своей фотографии заведения под рукой не было, поэтому сейчас там
акцентный градиент/текстура (честно, не выдаём за настоящее фото). Когда
появится реальное фото — заменить в `frontend/guide/index.html`, блок
`.home-hero` в CSS, на `background-image: url(...)` (комментарий рядом
с блоком показывает, куда именно).

**Что из ТЗ сознательно не сделано в этой версии** (можно добавить
отдельно, если понадобится): аналитика открытий/поиска (п. 29 ТЗ),
WebP/AVIF-конвейер для фото (для внутреннего инструмента с несколькими
десятками блюд это избыточно — `loading="lazy"` уже есть), импорт `.md`
пока не переносит новые поля (статус/FAQ/аллергены) — заводятся вручную
после импорта, как и фото раньше.

## Шаги деплоя

### 1. Backend

Скопировать `backend/oko-waiter-guide-api.js`, `backend/oko-waiter-guide-
store.js` и `backend/oko-waiter-guide-md-import.js` в папку существующего
бэкенда (туда же, где `oko-order-api.js`, `oko-inventory-api.js`).

В `.env` — отдельная переменная не нужна, использует тот же
`OKO_ADMIN_PASSWORD`, что и остальные админки OKO.

В точке входа бэкенда подключить:
```js
const { createOkoWaiterGuideRouter } = require("./oko-waiter-guide-api");
app.use("/api/oko-waiter-guide", createOkoWaiterGuideRouter());
```
Роутер ничего не отправляет в Telegram, `bot` не принимает.

Перезапустить процесс через pm2.

### 2. Frontend (статика, без сборки)

Скопировать так, чтобы получилось:
```
/home/kitchendesk/frontend/waiter-guide/index.html         <- frontend/guide/index.html
/home/kitchendesk/frontend/waiter-guide/admin/index.html    <- frontend/admin/index.html
```

**Нужна одна правка nginx** (в отличие от остальных модулей OKO) — у
каждого блюда и раздела теперь свой URL (`/waiter-guide/dish/tar-tar`,
`/waiter-guide/category/holodnye-zakuski`), а страница — статика без
собственного сервера, так что на этих путях нет настоящего файла на диске.
Нужен фолбэк на `index.html` именно для этих двух префиксов (общий
`location /` для остальных модулей менять не нужно, `/waiter-guide/admin/`
эта правка не касается — там свой файл есть):

```nginx
location ~ ^/waiter-guide/(category|dish)/ {
    try_files $uri $uri/ /waiter-guide/index.html;
}
```

Добавить этот блок в конфиг сайта (`server { ... }`, туда же, где остальные
`location`) **до** общего `location /`, перезагрузить nginx
(`nginx -t && systemctl reload nginx`).

Проверить:
```
curl -I https://kitchendesk.chefplan.ru/waiter-guide/
curl -I https://kitchendesk.chefplan.ru/waiter-guide/admin/
curl -I https://kitchendesk.chefplan.ru/waiter-guide/category/all
curl -I https://kitchendesk.chefplan.ru/waiter-guide/dish/несуществующий-слаг
```
Все четыре должны быть 200 (страница сама покажет «Блюдо не найдено» для
несуществующего слага — это код 200, ошибка отрисовывается в приложении,
не на уровне сервера).

### 3. Первый запуск

Открыть `https://kitchendesk.chefplan.ru/waiter-guide/admin/`, ввести
пароль. Создать разделы (как в присланном файле: Холодные закуски,
Салаты, Горячие закуски, Супы, Основной курс, Пасты, Пицца, Сувлаки,
Десерты, Хлеб, Закуски к пиву, Соусы), добавить блюда.

Ссылку для официантов — `https://kitchendesk.chefplan.ru/waiter-guide/`
— можно закрепить в рабочей Telegram-группе или отправить напрямую,
как ссылку на форму заказа.

### 4. Импорт блюд из файла (в самой админке)

В форме редактора есть карточка «Импорт блюд из файла» — загружаете `.md`
с блюдами, оформленными по образцу полей формы (порядок ниже, каждое
поле — необязательно, кроме названия), и все блюда заводятся разом, без
ручного ввода по одному:

```
## 1. Название блюда

**Подзаголовок:** текст (необязательно)

**Описание:**
текст

**История:**
текст (необязательно)

**Как подать гостю:**
«текст» (необязательно — кавычки-«ёлочки» по краям снимаются сами,
страница официанта сама оборачивает подачу в кавычки)

**Калькуляция:**
| Ингредиент | Ед. изм. | Кол-во |
|---|---|---|
| ... | ... | ... |

---
```

Блюда разделяются строкой `---`. Раздел, в который лягут все блюда файла,
можно либо выбрать вручную в форме, либо указать прямо в файле одной
строкой в начале: `Раздел везде один: **Название раздела**` — раздел
создаётся автоматически, если такого ещё нет, или довешивает блюда к уже
существующему с этим именем. У отдельного блюда раздел можно
переопределить полем `**Раздел:** Другое название` внутри его блока.

Фото не переносятся — их, как и раньше, добавляют потом вручную по
одному блюду через ту же форму.

Что осознанно не разбирается: любой текст в файле, который не начинается
с `## ` (преамбула в начале, примечания в конце вроде «не включено в этот
раз» или отдельный список полуфабрикатов) — он просто пропускается, и
редактор увидит в статусе после загрузки, сколько таких кусков было
пропущено, чтобы ничего не потерялось незамеченным.

**Проверено на реальном файле** (26 блюд суши и роллов, presланный
редактором) — прогнано через настоящий загруженный `.md` в браузере
(не только через API напрямую): все 26 блюд создались с верными
единицами измерения, вложенные кавычки внутри текста («…узнать по
«стенке» из нори») сохранились нетронутыми, а внешние кавычки-обёртка
вокруг «как подать гостю» корректно снялись даже когда после них шла
точка.

### 4а. Экспорт/импорт блюд через Excel (в самой админке — кнопка «Excel»)

Отдельно от `.md`-импорта — карточка «Блюда» в редакторе содержит кнопку
«Excel»: скачивает текущие блюда одной таблицей (`oko-waiter-guide-
xlsx.js`, лист «ттк» — одна строка на ингредиент, поле блюда объединено
в одну ячейку на весь его блок, ровно тот же формат, что уже был у
редактора для калькуляции), и принимает файл обратно тем же форматом —
существующие блюда (по служебной колонке `id`) обновляются, новые
(пустой `id`) заводятся. Раздел/подраздел/статус — по названию, заводятся
на лету, если такого ещё нет. Ничего не удаляется автоматически — блюдо,
пропавшее из файла, просто остаётся как было.

Два защитных исключения ради безопасности при обновлении: пустая ячейка
«раздел» не сбрасывает раздел блюда (просто не трогает), и пустой блок
состава (ни одной строки ингредиента) не стирает существующую
калькуляцию — все остальные поля переносятся ровно как в файле, пустая
ячейка стирает значение. Несколько таблиц состава на одно блюдо — строка
`[Название таблицы]` в колонке «ингредиент» без ед./кол-во, дальше её
ингредиенты как обычно.

**Нужна отдельная npm-зависимость на сервере** — `exceljs` (её не было
среди уже установленных). В папке бэкенда:
```
npm install exceljs
```
До этого шага `/admin/export-xlsx` и `/admin/import-xlsx` будут падать
с ошибкой require.

Проверено локально на реальном файле (16 блюд, 134 строки ингредиентов,
презланном редактором): полный цикл экспорт → правка → импорт без
расхождений, несколько таблиц состава через `[Label]`, оба защитных
исключения (пустой раздел/пустой состав), создание нового раздела на
лету при импорте, кнопка в реальном интерфейсе (скачивание + загрузка)
— через Playwright.

### 4б. Счётчик открытий и ссылка на пособие (вкладка «Настройки»)

Страница официанта — без логина и без имени (осознанно, см. выше), так
что узнать, КТО именно открыл, нельзя в принципе, не поломав это. Вместо
этого — анонимный счётчик: сколько раз открывали и в какие дни
(`data/guide-views.json`, растёт ограниченно — старше 90 дней не
хранится). Публичная страница шлёт `POST /guide-view` при каждом реальном
переходе (не при каждой перерисовке — иначе initial-boot задвоил бы
первый же просмотр). В «Настройках» рядом — сама публичная ссылка с
кнопкой «Скопировать» (раньше её только можно было увидеть, скопировать
было нечем).

Проверено через Playwright: реальный маршрут (главная → раздел → блюдо →
назад → главная) даёт ровно 5 открытий без дублей, кнопка «Скопировать»
кладёт в буфер обмена правильный URL.

### 5. Перенос присланного пособия (готовый импорт, одноразовый скрипт)

В папке `import/` — готовый одноразовый скрипт-импорт всего присланного
файла-пособия: 12 разделов, 72 блюда (описание / история / как подать /
калькуляция — там, где она была в исходнике). Фото не переносились —
их в исходном файле не было (см. `1.`), добавляются потом вручную через
админку по одному блюду.

```
cp import/import-waiter-guide.js import/waiter-guide-dataset.json <backend src dir>/
cd <backend src dir>
node import-waiter-guide.js
```

Скрипт отказывается работать, если в разделах или блюдах уже что-то
есть (чтобы не задвоить) — `--force`, если это осознанно (например,
добавить ещё поверх существующего).

**Калькуляция в исходном PDF — сама по себе картинка**, не текст (проверено
через анализ структуры PDF), поэтому автоматически извлечь числа было
нельзя — цифры перенесены вручную построчным чтением документа и один
раз сверены с повторно распознанной таблицей (совпало). Так как это
влияет на себестоимость, стоит пробежаться по нескольким блюдам в
админке после импорта, особенно по составным (Тар тар, Ассорти мезе,
Манго со страчателлой — несколько таблиц на одно блюдо).

19 блюд (в основном раздел «Соусы» и несколько других) в исходнике не
имели калькуляции вообще — там буквально стояло «место для калькуляции:
вставить после утверждения технологом» — они импортированы с пустой
калькуляцией, а не выдуманными числами; список выводится в консоль
после запуска скрипта.

Проверено локально: импорт даёт ровно 12 разделов / 72 блюда, составные
блюда (несколько таблиц на одно) корректно открываются и редактируются
в админке, и корректно разворачиваются на публичной странице для
официантов.

## Проверено локально перед деплоем

Полный цикл прогнан на тестовом сервере: раздел создан → блюдо с двумя
таблицами калькуляции (основа + гарнир) и фото → сохранено и корректно
подгружается обратно при повторном открытии формы редактирования (был
найден и исправлен баг — таблицы калькуляции не показывались при первом
открытии уже заполненного блюда, теперь показываются). Публичная
страница `/guide` отдаёт то же самое: фото, описание, цитата «как
подать», раскрывающийся блок с историей и обеими таблицами состава.
Удаление раздела проверено отдельно — блюдо не пропадает, корректно
попадает в «Без раздела» через `/admin/orphan-dishes`.
