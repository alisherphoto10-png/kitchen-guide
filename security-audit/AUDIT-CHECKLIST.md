# KitchenDesk — чек-лист безопасности (для серверной сессии)

Как и остальные служебные папки в этом репозитории — не код, а задание.
У меня (сессия Claude Code on the web) нет доступа к серверу, поэтому не
проверенное лично, а список конкретных пунктов, часть из которых — прямые
находки из истории этой же задачи, оставшиеся без ответа, часть — типовой
набор проверок для приложения такого профиля (Node/Express + Postgres +
React, аутентификация по паролю/PIN, интеграция со сторонним API с чужими
кредами, загрузка файлов, Telegram-боты).

Повод: проект вырос (не маленький, iiko-интеграция трогает реальные учётные
данные заведений), полноценного security-ревью реального кода ни разу не
было. Ничего конкретного не заподозрено — это профилактика, не реакция на
инцидент.

## 🔴 Критично — проверить первым

### 1. `users.plain_password`
В отчёте по Части 4 (`../oko-iiko-integration/REPORT-2026-08-11-part4.md`)
мельком упомянуто: «та же history-проблема уже тихо живёт в коде для
`users.plain_password`» — то есть в коде есть self-migrating `ALTER TABLE`
под колонку с таким именем в таблице `users`, которая тоже тихо фейлится по
правам (тот же паттерн, что был с `ttk`).

**Вопрос без ответа: пароли пользователей реально хранятся открытым
текстом в этой колонке, или она — неиспользуемый пережиток?**

- Если да — это открытый текст паролей всех сотрудников всех заведений.
  Нужно: перейти на хэширование (bcrypt/argon2), если ещё не используется
  нигде параллельно; понять, читает ли эту колонку живой код прямо сейчас
  (для логина или как fallback); принудительно сбросить пароли после
  миграции.
- Если колонка не используется — задокументировать это явно и, в идеале,
  удалить мёртвый код/колонку, чтобы не оставлять ловушку на будущее.

### 2. Секрет для подписи JWT
Сессия с доступом к серверу как минимум один раз входила под суперадмином,
подписав себе токен **тем же секретом, что использует бэкенд** (см. отчёт
про скриншоты для презентации, раздел «Как заходил»). Это рабочий и по-своему
элегантный способ получить доступ без сброса пароля владельца — но он же
показывает: тот, кто знает этот секрет, может выписать токен суперадмина на
**любой** ресторан без всякого пароля.

Проверить:
- Где хранится секрет (`.env`? захардкожен в коде?) — не должен быть нигде
  закоммичен, если код когда-либо попадёт под git.
- Есть ли что-то ещё в проверке токена, кроме подписи (issuer/audience,
  список отозванных токенов) — или валидная подпись достаточна сама по
  себе.
- Ротировался ли этот секрет когда-либо; стоит ли ротировать сейчас, раз
  как минимум мне (в чате) он не передавался, но сама техника его
  использования — задокументирована в git-истории этого репозитория.

## 🟠 Высокий приоритет

### 3. TLS к iiko (`rejectUnauthorized: false`)
Уже известный, много раз отмеченный пункт — сейчас проверка сертификата
демо-стенда отключена. С учётом того, что как минимум один реальный демо-
доступ (логин/пароль/пинкод) уже прошёл через этот канал — время вернуться
к этому пункту, не откладывать до «первого боевого заведения».

### 4. Шифрование `iiko_connections.password_encrypted`
Само по себе шифрование уже сделано (AES-256-GCM, по документации Части 1).
Проверить вокруг него:
- Где хранится `IIKO_CREDENTIALS_ENCRYPTION_KEY` — тот же `.env`, что уже
  один раз ловил баг с обрезанием по `#`? Убедиться, что ключ не обрезан и
  не хранится ещё где-то по совместительству.
- Логируется ли где-нибудь расшифрованный пароль (например, в тексте
  ошибки при неудачной авторизации к iiko) — это была бы утечка через логи,
  а не через БД.
- Ротировался ли ключ шифрования хоть раз с момента создания.

### 5. Права на таблицы БД / процесс миграций
`ttk` (и, возможно, `users`) принадлежат роли `postgres`, а не рабочей роли
приложения — миграции накатываются вручную через `sudo -u postgres psql`, в
обход кода. Это не уязвимость сама по себе, но:
- Означает отсутствие единого прослеживаемого процесса миграций — сложно
  понять, что реально накатано на проде, без ручной проверки.
- Стоит либо поправить владельца таблиц на рабочую роль (стандартный путь),
  либо явно задокументировать процесс «миграции только вручную через sudo»
  как осознанное решение, а не случайность.

### 6. Зависимости
`npm audit` (и бэкенд, и фронтенд) — начиная от известных CVE, особенно
учитывая, что код не под git и историю обновлений зависимостей проследить
нельзя обычным способом (`git log package-lock.json`).

### 7. Обработка ошибок в проде
Проверить, что API в production-режиме не возвращает клиенту стек-трейсы,
пути на сервере или другие внутренние детали в теле ошибки — только
безопасное сообщение.

### 8. Загрузка фото ТТК
Куда сохраняются загруженные фото блюд (локальный диск/облако), кто может
их читать (публично доступны по прямой ссылке — это нормально для фото
блюда, но стоит проверить осознанно, а не по умолчанию), есть ли проверка
типа/размера файла на эндпоинте загрузки.

## 🟡 Средний приоритет

### 9. PIN-логин без ограничения попыток
Вход в KitchenDesk поддерживает PIN-код (короче и проще, чем пароль — ниже
энтропия). Проверить: есть ли лимит попыток / временная блокировка после
нескольких неверных PIN, или можно перебирать без ограничений.

### 10. `oko-order-relay` submit-эндпоинт
В собственной документации модуля уже отмечен как принятый риск для MVP:
«submit технически может вызвать кто угодно, кто знает адрес формы». Стоит
пересмотреть, актуально ли это допущение сейчас, когда система в целом
выросла — тот же риск, что и раньше, просто стоит спросить ещё раз, не
считать решённым навсегда.

### 11. Cookie/CSRF
Если используются cookie для сессии — проверить флаги `HttpOnly`, `Secure`,
`SameSite`. Если сессия целиком на JWT в заголовке — этот пункт менее
актуален, но стоит подтвердить, как оно на самом деле устроено.

## Процессное (не совсем «безопасность», но усиливает всё остальное)

### 12. Код всё ещё не под git
Отмечено уже несколько раз по ходу этой задачи. Помимо прочего, это
затрудняет: аудит истории изменений, откат при инциденте, поиск, кто и
когда внёс конкретную правку. Не обязательно публичный git — но версионный
контроль хоть в каком-то виде (даже приватный локальный репозиторий на
сервере) сильно облегчит вообще всё, включая безопасность.
