# Структурированный состав ТТК — Часть 0: схема полей и план миграции

Новая инициатива, отдельная от `oko-iiko-integration` и `banquet-calculator`
(хотя тесно связана с обеими). Причина, по словам пользователя: интеграция
с iiko будет доступна не на минимальном тарифе KitchenDesk, а на
максимальном. Значит выгодно уже сейчас перевести состав ТТК на
структурированные поля **для всех пользователей**, а не только для тех, у
кого подключена iiko — чтобы при апгрейде тарифа данные iiko просто
«вставали» в уже готовую структуру («вилка в розетку»), без миграции и без
риска что-то сломать.

**Это Часть 0 — только план и схема, без реализации.** Реализация будет
отдельными частями после согласования схемы.

## Напоминание фактов (из предыдущих частей этого же большого разговора)

- Сейчас состав ТТК (`ttk.ingredients`) — **свободный текст**, без
  исключений, даже у ручных (не-iiko) блюд. Разный формат: запятая или
  перенос строки как разделитель (см. `oko-iiko-integration`, разведка
  структуры).
- В `banquet-calculator` уже написан (и неплохо проверен) **regex-парсер**
  свободного текста в пары «название — количество — единица», плюс логика
  распознавания и раскрытия полуфабрикатов по префиксу «пф»/«п/ф». Это
  можно и нужно переиспользовать как основу для миграции существующих
  данных, а не писать парсинг заново.
- У iiko (`assemblyCharts`) состав хранится структурированно: брутто,
  нетто, % потерь по каждому ингредиенту (см. `oko-iiko-integration`,
  Часть 5).
- Категория «полуфабрикат» — тоже просто текст в `ttk.category`, не
  отдельная сущность, регистр не нормализован («полуфабрикат»/
  «Полуфабрикат»).

## Предлагаемая схема полей (для обсуждения/подтверждения)

Цель — чтобы поля совпадали с тем, что реально может отдать iiko, без
лишнего преобразования при подключении интеграции позже:

Новая таблица (например `ttk_ingredients`) вместо текстового поля:
- `id`
- `ttk_id` — ссылка на блюдо (не текстовое имя, как сейчас у ПФ-ссылок —
  реальный внешний ключ).
- `name` — название ингредиента (текст).
- `brutto` — масса брутто (число).
- `netto` — масса нетто (число).
- `loss_percent` — % потерь (число, может быть пустым/0).
- `unit` — единица измерения (кг/г/л/мл/шт — как отдельное поле, не часть
  текста).
- `is_semi_finished` (boolean) или `linked_ttk_id` (ссылка на другой ттк,
  если ингредиент — это полуфабрикат, ссылающийся на другую карту) —
  **этот момент особенно важный**: сейчас связь ПФ↔блюдо только по
  совпадению текстовых названий (хрупко, ловили баги на этом в
  banquet-calculator). Если переходим на структуру — стоит сразу сделать
  **настоящую ссылку по id**, а не по имени, раз всё равно всё меняем.

Открытый вопрос пользователю: подтвердить, что именно эти поля нужны
(brutto/netto/loss_percent/unit), или что-то упростить/добавить.

## Уточнение от пользователя (после первого варианта макета) — два добавления

### 1. Выход блюда — два отдельных поля, не одно

Сейчас в схеме выше выхода блюда вообще нет (только поля на уровне
ингредиента). Нужно добавить на уровне самого `ttk`:
- `yield_weight` — выход по весу (число + единица, кг/г/л/мл).
- `yield_count` — выход поштучно (число, шт).

Оба поля не обязательны одновременно — у блюда может быть только один из
них (например «Крем-суп дня» — только весовой) или **оба сразу** (реальный
пример от пользователя: «Греческие пирожки» — состав весовой, а выход и
900 г, и 10 шт одновременно, из одной раскладки). Не путать «поле пустое»
(нет данных) с «0» (числовой ноль) — на UI пустое поле должно показываться
как прочерк/«не указано».

**Требует отдельной разведки перед тем, как закладывать в схему как факт**:
действительно ли у iiko (`assemblyCharts` или карточка товара-блюда) выход
хранится именно как два раздельных поля (весовой и штучный) — предыдущая
разведка (Часть 5 `oko-iiko-integration`) фиксировала брутто/нетто/%
потерь **по ингредиентам**, но не структуру выхода **самого блюда**. Это
наблюдение пользователя с реальной кухни, не подтверждённый факт по API —
сначала проверить, потом опираться.

### 2. Два уровня детализации в интерфейсе — повар и администрация

Согласованный макет:
https://claude.ai/code/artifact/0f917f9d-4da2-4e4d-a6ce-7b47f83d47fd

- **Вид повара** (только чтение) — упрощённый: название ингредиента +
  брутто (без нетто/% потерь), и блок «Выход» — одна или две плашки
  (весовой/штучный), в зависимости от того, что заполнено у блюда.
- **Вид администрации** (редактор, полная номенклатура) — все поля:
  брутто/нетто/%потерь/единица по ингредиентам, плюс оба поля выхода
  отдельно подписанные («Весовой» / «Штучный»), с явным «не указано» для
  пустого, а не 0.

Это не меняет схему данных (одна и та же структура в БД), только то, какие
поля показываются каждой роли на фронтенде.

## План миграции существующих 456 строк

1. Написать (или переиспользовать логику из `banquet.js`) скрипт разбора
   текущего `ttk.ingredients` (текст) → предполагаемые
   `name`/`brutto` (или единственное число, если брутто/нетто в тексте не
   различить — скорее всего в текущем тексте вообще нет разделения
   брутто/нетто, только одно число; это нужно учесть — куда класть
   единственное известное число, в `brutto` или `netto`, с пометкой, что
   второе поле не заполнено, а не выдумано).
2. Прогнать разбор **в режиме отчёта, не записи** — показать, сколько
   строк разобралось однозначно, сколько нет (аналог стресс-теста из
   `banquet-calculator` Части 1) — не переносить в новую схему то, что не
   разобралось, эти блюда останутся с пометкой «требует ручной проверки».
3. Обсудить с пользователем результат разбора, только затем переносить
   данные по-настоящему.
4. Связи ПФ (по имени) — при миграции пытаться сопоставить с реальным
   `ttk_id` по точному совпадению названия (регистронезависимо); что не
   сопоставилось — оставить как обычный ингредиент с пометкой «возможно,
   это полуфабрикат, не сопоставлено», не терять информацию молча.

## Что это меняет в уже существующем функционале (только перечислить, не делать в этой части)

- **Карточка ТТК** (редактор) — вместо textarea для состава: построчный
  ввод (название + брутто + нетто + % потерь + единица на строку,
  добавление/удаление строк).
- **Банкет-калькулятор** — для блюд с уже структурированным составом можно
  считать напрямую по числам, без regex — надёжнее и без предупреждений
  «не распознано». Для ещё не мигрированных — старый парсер остаётся как
  временный запасной путь, не удалять его сразу.
- **Импорт из iiko** (`ttk-import`, вариант А) — придётся переписать: не
  сериализовать состав в текст, а писать в новую структуру. Это отменяет
  часть решения «вариант А» из `oko-iiko-integration` — явно предупредить,
  что это осознанное изменение прошлого решения, не забытая часть.
- Экспорт ТТК (если есть, кнопка «Экспорт» на карточке блюда) — сверить
  формат экспорта, не сломать.
