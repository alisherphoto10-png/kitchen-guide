## 1.1 — Схема БД: подтверждено

Таблица `ttk_ingredients` существует в `oko_kitchen`, владелец — `oko_user`
(не `postgres`, ловушка из security-аудита учтена):

```
ttk_ingredients(id, ttk_id FK→ttk(id) ON DELETE CASCADE, sort_order,
  name, brutto, netto, loss_percent, unit, linked_ttk_id FK→ttk(id) ON DELETE SET NULL,
  created_at, updated_at)
```

Индексы на `ttk_id` и `linked_ttk_id` есть. `linked_ttk_id` — настоящий FK,
не текстовое имя, как и требовалось.

На `ttk` добавлены: `yield_weight`, `yield_weight_unit`, `yield_count`,
`needs_manual_review` (boolean, default false), `yield_weight_computed`
(boolean, default false — помечает довычисленный при iiko-импорте вес, не
пришедший от iiko напрямую).

Миграции колонок/таблицы идемпотентны (`ADD COLUMN IF NOT EXISTS` /
`CREATE TABLE IF NOT EXISTS`), выполняются автоматически при старте
backend (`src/api/ttk.js`, строки 65–100).

## 1.3 — Карточка ТТК: вкладки «Вручную» / «Импорт из файла»: реализовано, на веб и `/cabinet/`

`/cabinet/` — это не отдельная сборка, а тот же Next.js SPA (root
`page.tsx` с Telegram WebApp детектом), который nginx отдаёт по
`location /cabinet/` с fallback на тот же `index.html`, что и вся
Mini App — поэтому один responsive-компонент действительно покрывает и
веб, и мобильную версию, как и требовалось.

Компонент `TtkIngredientsEditor` (`Admin.tsx`, ~строки 717–951):
- Вкладки «Вручную»/«Импорт из файла» — есть.
- «Вручную»: на `sm+` — построчная таблица (название/брутто/нетто/%
  потерь/ед.), добавление/удаление строк; на `<sm` — карточная раскладка
  (один ингредиент = один блок, поля друг под другом), тот же приём, что
  в `banquet-calculator` Части 8 — колонки не сжаты до нечитаемости.
- «Импорт из файла»: drag-and-drop на вебе + обычный `<input type=file>`
  на мобильном (тот же элемент, drag просто не используется жестом),
  превью с подсветкой нераспознанных строк (оранжевым), кнопка
  «Импортировать N строк» вносит только распознанные. Переиспользует
  библиотеку `xlsx`, как и было решено (не с нуля).
- Поле «Выход» — два независимых поля (весовой с выбором кг/л, штучный),
  довычисленное значение помечено «≈ вычислено».
- Связь полуфабрикатов по имени резолвится на бэкенде
  (`db.resolveLinkedTtkIds`) — форма не требует отдельного поля выбора.

## 1.4 — Разделение по ролям на отображение: реализовано

`Search.tsx`: `EDITOR_ROLES = ['admin', 'chef', 'sushef', 'superadmin']` —
тот же список, что и в других местах проекта (не изобретён заново).
- Повар (не входит в `EDITOR_ROLES`) — `IngredientsTable`: только
  название + количество, без брутто/нетто/%потерь.
- Администрация — `StructuredIngredientsTable`: полная номенклатура
  (брутто/нетто/%потерь/ед.), тот же responsive-приём (таблица/карточки).
- «Выход» — одна или две плашки в зависимости от заполненности, видно
  обеим ролям (это не спорная часть, доступ различается только у состава).

## 1.5 — Не сломать существующее: реализовано

- **Банкет-калькулятор** (`banquet.js`): добавлен `parseStructured` —
  считает напрямую по числам из `ttk_ingredients`/`yield_weight`/
  `yield_count`, без regex и без LIKE-поиска ПФ по имени (используется
  настоящий `linked_ttk_id`). Решение, каким путём считать конкретный
  ттк, принимается по факту наличия строк и `needs_manual_review`
  (функция есть в файле, строки ~108–114). Старый текстовый парсер
  (`lineRe`, строка 181) не удалён — остаётся рабочим запасным путём для
  немигрированных блюд. Ветки, где данные не готовы (ещё нет строк,
  `needs_manual_review`, циклическая ссылка, ттк не найдено) — не
  подмешиваются молча как 0, идёт явный warning в общий список.
- **Импорт из iiko** (`ttk-import`, `admin.js` ~2137–2287): переписан —
  пишет структурированно в `ttk_ingredients`, свободный текст
  `ttk.ingredients` для iiko-блюд больше не пишется. Осознанный откат
  «варианта А» отмечен явным комментарием в коде. Маппинг выхода —
  вариант 1 из отчёта Части 0 (mainUnit кг/л → `yield_weight` напрямую;
  mainUnit шт/порц → `yield_count` напрямую + довычисленный
  `yield_weight` через `unitWeight`, помечен `yield_weight_computed`).
- **Экспорт ТТК**: не переписывался отдельно и не должен был — `Search.tsx`
  ещё до передачи в `ExportMenu`/`ttkExport.ts` приводит оба источника
  (`ingredientsStructured` или старый текст) к одной и той же форме
  `{name, qty}`; экспорт не знает, каким путём посчитано, и не сломан.
- **Часть 4 `oko-iiko-integration` (блокировка редактирования для
  iiko-блюд)**: продолжает работать и распространена на новые поля —
  `PUT /api/admin/ttk/:id` при `iiko_managed_at != null` игнорирует
  присланные `ingredientsStructured`/`yield_weight`/`yield_weight_unit`/
  `yield_count`/`yield_weight_computed` независимо от тела запроса
  (защита не только в UI, но и на прямой запрос к API), UI-часть
  редактора получает `disabled` и блокируется тем же предупреждением.

## Результаты проверки (пункты 1–6 из ТЗ) — по коду, не вживую

Проверялось чтением кода и состояния БД, не кликами в реальном интерфейсе
(интерактивный проход по UI в рамках этой сессии не делался):

1. Сохранение вкладки «Вручную» → пишет в `ttk_ingredients`
   (`replaceTtkIngredients`), не в старый текст — подтверждено по коду
   `admin.js` (`PUT /api/admin/ttk/:id`, `POST /api/admin/ttk`).
2. Импорт xlsx — превью с подсветкой нераспознанных, импортирует только
   распознанные строки — подтверждено по коду `TtkIngredientsEditor`.
3. Повар видит упрощённый вид, администрация — полный, на одном и том же
   блюде — подтверждено по коду `Search.tsx` (`canEdit` ветвление).
4/5. Расчёт банкета по мигрированному/немигрированному блюду — подтверждено
   по коду `banquet.js` (`parseStructured` vs `lineRe`-парсер, ветвление по
   наличию строк/`needs_manual_review`); реальный расчёт банкета в этой
   сессии не запускался.
6. iiko-блюдо — состав по-прежнему не редактируется вручную — подтверждено
   по коду (см. 1.5 выше); живой клик по форме не делался.

**Рекомендация**: следующий шаг — реальный клик по интерфейсу (создать/
отредактировать не-iiko блюдо, прогнать тестовый xlsx, посмотреть карточку
под учёткой повара, прогнать банкет с мигрированным и немигрированным
блюдом) — этот отчёт подтверждает, что код и данные на месте, но не
заменяет визуальную проверку вживую.
