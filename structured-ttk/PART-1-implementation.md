# Часть 1 — реализация структурированного состава ТТК

**Делать после Части 0** (разведка/схема/пробный разбор в режиме отчёта).
Если Часть 0 ещё не выполнена или её результаты не читались — сначала
пройти её, реальная схема ниже подтверждается/корректируется по факту
разбора 456 строк, не наоборот.

Два согласованных макета — использовать как визуальный референс:
- Повар (упрощённо) vs администрация (полная номенклатура) + два поля
  выхода: https://claude.ai/code/artifact/0f917f9d-4da2-4e4d-a6ce-7b47f83d47fd
- Ручной ввод построчно + импорт из xlsx с превью:
  https://claude.ai/code/artifact/840d6dd8-1d0f-467a-9f94-610c6bd9fee4

Пользователь прямо сказал: правки будут по ходу живого тестирования —
не нужно добиваться идеала до деплоя, важнее получить рабочую версию,
которую можно пощупать, и дальше итерировать (как с банкет-калькулятором).

## 1.1 — Схема БД

По итогам Части 0 (со скорректированной схемой, если разбор её изменил):
- Новая таблица под ингредиенты (`ttk_ingredients` или как решится по
  факту прав/владения таблиц — **не забыть проверить владельца новой
  таблицы сразу**, учитывая уже дважды пойманную проблему `postgres` vs
  `oko_user` из security-аудита — сразу создать с правильным владельцем,
  не откладывать).
- `ttk.yield_weight` / `ttk.yield_count` — оба необязательные, независимо
  друг от друга.
- Связь полуфабрикатов — по `linked_ttk_id` (реальный id), не по имени.

## 1.2 — Миграция существующих данных

По результату дозорного разбора из Части 0: перенести то, что разобралось
однозначно, оставить явную пометку (например `needs_manual_review = true`
на строке `ttk`) у того, что не разобралось — эти блюда **не должны молча
остаться с пустым составом**, админ должен видеть, что их нужно
доразобрать вручную.

## 1.3 — Карточка ТТК: вкладки «Вручную» / «Импорт из файла»

Как в макете:
- **Вручную** — построчная таблица (название/брутто/нетто/%потерь/
  единица), добавление/удаление строк, поле «Выход» с двумя независимыми
  полями (весовой/штучный, оба необязательны).
- **Импорт из файла** — drag-and-drop xlsx, ссылка на шаблон, превью перед
  подтверждением с подсветкой нераспознанных строк (не молча пропускать —
  тот же принцип честных предупреждений, что уже реализован в
  банкет-калькуляторе). Адаптировать под новый формат уже существующий в
  проекте xlsx-импорт ТТК, не писать с нуля, если получится переиспользовать
  парсинг файла.

## 1.4 — Разделение по ролям на отображение

- Повар (read-only) — упрощённая карточка: название + брутто на
  ингредиент, выход (одна или две плашки, в зависимости от заполненности).
- Администрация (редактор) — полная номенклатура, как в 1.3.

## 1.5 — Не сломать существующее

- **Банкет-калькулятор**: для блюд с уже структурированными данными —
  считать напрямую по числам (`brutto`/`netto` из новой таблицы), без
  regex. Для ещё не мигрированных (`needs_manual_review` или просто нет
  строк в новой таблице) — старый текстовый парсер остаётся рабочим
  запасным путём, не удалять его в этой части.
- **Импорт из iiko** (`ttk-import`): переписать так, чтобы писал в новую
  структурированную таблицу, а не сериализовал в текст. Это осознанно
  отменяет прошлое решение «вариант А» — явно отметить это в отчёте, не
  как забытую деталь.
- **Экспорт ТТК** (если есть кнопка «Экспорт» на карточке) — сверить,
  что не сломался под новую структуру данных.
- Часть 4 из `oko-iiko-integration` (блокировка редактирования состава для
  iiko-блюд) — логика должна продолжать работать: если блюдо `iikoManaged`,
  строки ингредиентов в новой таблице тоже должны быть не редактируемы
  вручную, с тем же предупреждением, что уже показывается.

## Проверка

1. Открыть карточку не-iiko блюда → вкладка «Вручную» → добавить/изменить
   ингредиент → сохранить → данные реально в новой структуре, не в старом
   тексте.
2. Импорт xlsx на тестовом файле — превью с нераспознанными строками (если
   есть), подтверждение импортирует только валидные строки.
3. Повар видит упрощённый вид, администрация — полный, на одном и том же
   блюде.
4. Банкет с уже мигрированным блюдом — расчёт идёт по числам напрямую (без
   warning про нераспознанный текст, если раньше был).
5. Банкет со всё ещё не мигрированным блюдом — старый парсер по-прежнему
   работает, ничего не сломалось.
6. iiko-блюдо — состав по-прежнему не редактируется вручную (Часть 4
   `oko-iiko-integration` не регрессировала).

## Отчёт

Что реализовано, что отличается от макетов и почему (если пришлось
отклониться), результаты проверки 1-6, и отдельно — что мигрировалось
автоматически, а что осталось с пометкой «требует ручной проверки» (с
конкретным списком/количеством).
