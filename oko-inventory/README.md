# OKO Inventory — инструкция по деплою

Инструмент для инвентаризации кухонной утвари одной кухни: каталог позиций
(название, категория, размер, фото, единица измерения), приход/списание с
датой и причиной, текущий остаток, экспорт в Excel за произвольный период —
по образцу присланного файла-таблицы. Пользователь один — администратор,
отдельного доступа для поваров нет.

Это временная папка-склад в репозитории `kitchen-guide` — сюда код попал
только для передачи на сервер, как и `oko-order-relay/`. После деплоя эту
папку из репозитория можно удалить.

## Структура

```

  oko-inventory-api.js       — Express-роутеры:
                                  createOkoInventoryRouter(bot)      — items, movement, export, photos, drafts, recount-админка (весь роутер за X-Admin-Password)
                                  createOkoInventoryCountRouter()    — публичный роутер для страницы повара (без пароля, доступ по токену ссылки, см. ниже)
  oko-inventory-store.js     — файловое хранилище (JSON) + расчёт остатков
  oko-inventory-telegram.js  — слушатель фото в теме списаний, разбор подписи, подбор позиции
  oko-known-chats.js         — тот же общий файл, что и в oko-order-relay (для выпадающего списка групп/тем)
  data/                       — создаётся автоматически при первом запуске
    oko-inventory-items.json
    oko-inventory-movements.json
    oko-inventory-categories.json      — категории утвари (см. ниже)
    oko-inventory-drafts.json          — черновики из Telegram (см. ниже)
    oko-inventory-recounts.json        — сессии полного пересчёта (см. ниже)
    oko-inventory-telegram-config.json — какую группу/тему слушать
    photos/                   — фото позиций и черновиков, отдельными файлами
```

## Вкладки в админке (ПК-раскладка)

Раньше всё было одной длинной страницей — переросло в отдельные вкладки с
боковой панелью слева (как на десктопных админках), переключение без
перезагрузки:

- **Входящие** — черновики из Telegram, счётчик на самой вкладке (красный
  бейдж), открывается первой при входе.
- **Позиции** — каталог: поиск, фильтр по категориям, инлайн-смена
  категории, приход/списание/история по каждой. Сверху — кнопки
  «+ Добавить позицию» и «📥 Экспорт», обе открывают модальное окно.
- **Пересчёт** — полная физическая инвентаризация: ссылка для поваров,
  живой прогресс, сверка с системой (см. отдельный раздел ниже).
- **Категории** — управление категориями (было отдельной карточкой на
  главной, просто переехало).
- **Настройки** — только подключение Telegram-темы (экспорт переехал на
  вкладку «Позиции», см. выше).

**Добавление позиции и экспорт — модальные окна**, а не карточки на
странице: нажатие на кнопку открывает окно поверх текущего вида, всё
содержимое (поля формы/выбор периода и формата) то же самое, что было
раньше, просто в оверлее. Закрывается крестиком, кликом мимо окна или
(для добавления позиции) автоматически через секунду после успешного
добавления.

**Мобильная навигация — как в пособии официанта**: на узких экранах
боковая панель прячется, вместо неё — верхняя панель с кнопкой-гамбургером
(☰), открывающей выдвижную панель справа с теми же 4 пунктами (и тем же
бейджем счётчика черновиков) — клик по пункту переключает вкладку и сразу
закрывает панель. Раскладка карточек внутри вкладок не менялась, адаптация
была именно под навигацию.

## Категории утвари

Позиция каталога может относиться к одной категории (`categoryId`) или быть
без категории. Категории — свой управляемый список (карточка «Категории» в
админке: добавить, переименовать, удалить), а не просто текст на позиции —
так фильтр в списке позиций всегда показывает реальный, не «расползшийся»
набор категорий, а не произвольные опечатки в свободном поле.

Удаление категории не удаляет и не архивирует позиции в ней — они просто
становятся «без категории», их остатки и история движений не трогаются.

У каждой позиции в списке — маленький выпадающий список категории прямо в
строке (меняется сразу по выбору, без отдельной формы редактирования) —
удобно быстро разложить по категориям уже существующие позиции (например,
225 позиций из разового импорта, см. ниже).

## Приход/списание из Telegram (черновики на подтверждение)

Повар кидает **фото + короткую подпись** в настроенную тему группы поваров
(например «разбили 2 тарелки» или «пришло 10 половников») — бот **не
применяет движение сразу** (свободный текст ненадёжен для реальных цифр
склада), а готовит черновик:

- определяет тип по ключевым словам в подписи — «пришло/принесли/купили/
  закупили» → приход, всё остальное (включая просто число без слов) →
  списание, это дефолт темы;
- вытаскивает число из подписи — количество;
- угадывает позицию каталога по оставшемуся тексту (сравнение по словам,
  с запасом на падежи и лишние слова вроде «повар уронил»);
- скачивает и сохраняет фото.

Бот сразу отвечает в теме, что понял («Похоже на: Тарелка обеденная,
Количество: 2, Тип: списание») — так повар сразу видит, если бот понял
неправильно. Владелец разбирает черновики не обязательно в тот же день —
может копиться и разбираться раз в неделю, поэтому это сообщение не просит
"подтвердить в админке" (это и так подразумевается) и не дублируется новым
сообщением при подтверждении — **то же самое сообщение потом
редактируется** на «✅ Записано» (id сообщения запоминается на черновике,
см. `botReplyMessageId`), а не улетает второе поверх в тему. Если
редактирование почему-то невозможно (например, отправка первого сообщения
не удалась) — подтверждение подстрахуется обычной отправкой нового.

**В админке** — карточка «Из Telegram» наверху страницы, появляется только
когда есть неподтверждённые черновики. У каждого — фото, кто прислал,
исходный текст, до 3 похожих позиций-кандидатов с процентом уверенности
(клик по любому — сразу выбирает её), степпер количества (−/+, тут же
живой пересчёт «Было: X шт → Станет: Y шт» по текущему остатку выбранной
позиции), переключатель приход/списание. «Подтвердить» — записывает
обычное движение (с тем же фото и пометкой «Telegram: Имя» в примечании).
«Отклонить» — черновик пропадает, на остатки не влияет, сообщение в теме
не трогается.

Если бот не нашёл ни одного похожего варианта (например, позиции ещё нет в
каталоге) — под фото написано «Похожих позиций не нашлось», а рядом с
«Подтвердить»/«Отклонить» есть кнопка **«Создать новую позицию»** — мини-
форма прямо в карточке черновика (название — подсказка из подписи,
категория, ед. изм.), которая создаёт позицию, переиспользуя уже
скачанное фото черновика (повторно загружать не нужно), и сразу
подставляет её в выбор — остаётся нажать «Подтвердить».

**Реагирует только на сообщения с фото** — просто текст в этой теме бот
игнорирует (это может быть обычный чат, не сигнал для склада).

### Настройка группы/темы

В админке — карточка «Настройки Telegram»: выбрать группу/тему из списка
(бот запоминает их сам, см. `oko-known-chats.js`) или ввести Chat ID / Thread
ID вручную. Узнать ID, не заходя в админку — написать `/okoid` прямо в
нужной теме.

## Пересчёт утвари (полная физическая инвентаризация)

Отдельный флоу от черновиков выше — там повар шлёт единичное фото на одно
движение (приход/списание), тут владелец раз в какое-то время объявляет
разовую сессию, где несколько поваров физически обходят кухню и вбивают
**фактическое** количество по каждой позиции, а не отдельное движение.

**Как пользоваться (вкладка «Пересчёт» в админке):**

1. **Настройка** — выбрать, за какой период действует ссылка (даты «с» и
   «по»), и отметить галочками, какие категории считаем (крупную технику,
   мебель и т.п. можно не отмечать — сразу видно, сколько позиций попадёт
   в пересчёт из общего числа). «Создать ссылку» — создаёт сессию,
   автоматически закрывая предыдущую незавершённую, если такая была (одна
   активная сессия единовременно).
2. **Пока пересчёт идёт** — ссылка вида `/count/<токен>` (кидается поварам
   в чат вручную, кнопка «Скопировать»), общий прогресс, разбивка по
   категориям, лента последних записей (кто что вбил и когда). Обновляется
   само по себе раз в 6 секунд, пока открыта эта вкладка.
3. **«Завершить и сверить»** — закрывает сессию (повара больше не смогут
   вбивать), открывает таблицу сверки: ожидалось по системе / посчитано /
   разница. Совпадения можно принять все разом одной кнопкой; расхождения —
   по одному, с полем «причина» перед принятием. «Принять» создаёт обычное
   корректирующее движение (`addMovement`, тип зависит от знака разницы,
   причина в примечании «Корректировка по пересчёту — ...») — остаток НЕ
   трогается сам по себе, пока это явно не подтверждено.

**Доступ поваров — не по паролю админки.** `createOkoInventoryCountRouter()`
— отдельный, не защищённый `requireAdmin` роутер (у
`createOkoInventoryRouter()` он навешан на весь роутер целиком через
`router.use`, поэтому проще завести второй роутер, чем разбирать
авторизацию по каждому урлу там). Секрет — сам токен сессии в ссылке
(`crypto.randomBytes(16).toString("hex")`, генерируется в
`createRecountSession`), а не общий пароль.

**Несколько поваров одновременно — без ручного распределения.** Все видят
один и тот же общий список (как в знакомом инструменте пересчёта
продуктов — один аккаунт, несколько устройств, всё синхронизировано):
как только кто-то вписал количество, позиция сразу помечается «✓ N шт —
Имя» и видна остальным при следующем опросе сервера (раз в 5 секунд).
Блокировок/захвата категорий нет — рассматривалось и отклонено в пользу
этой более простой и уже привычной пользователю модели. Если два повара
одновременно (в одну секунду) впишут одну и ту же позицию — побеждает тот,
кто отправил последним, без предупреждения о конфликте (сознательный
компромисс: для физического пересчёта это маловероятно, повара по факту
обходят разные углы кухни).

**Повару принципиально не показывается остаток по системе** — только факт
«посчитано / не посчитано» — иначе повар может просто переписать «сколько
должно быть» вместо того, чтобы реально пересчитать. `recountCountList()`
в сторе отдаёт `items` без поля `balance` специально для этого; сверка
с системным остатком — только на стороне владельца, после закрытия сессии.

**Данные сессии** — `data/oko-inventory-recounts.json`, массив объектов
`{id, token, categoryIds, validFrom, validUntil, closedAt, entries}`, где
`entries` — словарь `itemId → {qty, by, at, accepted, acceptedAt}`. Список
позиций для конкретной сессии не «замораживается» на момент создания —
считается на лету по текущему `categoryIds` (если позицию добавили в
подходящую категорию уже после создания сессии, она тоже попадёт в список).

## Как это устроено

**Остаток = сумма движений.** У позиции нет отдельного поля «остаток» —
при создании позиции с ненулевым «начальным количеством» это просто
записывается как обычное движение с типом «приход» и причиной «начальный
остаток», датированное днём создания. Текущий остаток — сумма всех
«приход» минус сумма всех «списание» по этой позиции. Экспорт за период
[from, to] считает то же самое, но раздельно: остаток на начало периода —
сумма движений **до** `from`, приход/списание — сумма движений **внутри**
периода, остаток на конец — их сумма.

**Дата движения из черновика Telegram — день, когда повар прислал фото, а
не день, когда владелец подтвердил черновик в админке** (это может
случиться неделю спустя, см. выше про редактирование сообщения) —
`POST /drafts/:id/confirm` передаёт в `addMovement` дату из
`draft.createdAt`, а не оставляет её на "сегодня" по умолчанию. Иначе
экспорт за период показывал бы списание задним числом в чужом периоде —
например, повар разбил тарелку 10 сентября, а владелец подтвердил только
17-го: без этой правки движение бы легло на 17 сентября.

**Фото хранятся отдельными файлами**, не внутри JSON — `oko-inventory-
items.json` остаётся компактным даже с сотней позиций с фото. Раздаются
через `GET /api/oko-inventory/photos/:filename`, за паролем (как и всё
остальное в этом роутере) — админка получает их через `fetch` с заголовком
и показывает как blob-URL, обычный `<img src="...">` так не сможет
(браузер не добавит кастомный заголовок к обычной загрузке картинки).

**Экспорт в Excel** — `GET /api/oko-inventory/export?from=YYYY-MM-DD&to=YYYY-MM-DD`,
отдаёт настоящий `.xlsx` (библиотека `exceljs`) с колонками: №,
Наименование, Фото (миниатюра встроена в ячейку), размер, Остаток на
начало <дата>, Ед. изм, Примечание, Приход, Списание, Остаток на конец
<дата> — тот же порядок колонок, что в присланном файле-образце. Этот
макет НЕ менялся — специально повторяет формат исходной таблицы
пользователя.

**Экспорт в PDF** — `GET /api/oko-inventory/export-pdf?from=...&to=...`,
второй раз переработан (по присланному пользователем ТЗ на "официальный
складской документ": минимализм, белый фон, крупное фото, тонкие
разделители вместо тяжёлых рамок) с несколькими правками уже по месту, по
живым скриншотам:

- **A4, альбомная ориентация** — ТЗ просило книжную, но с 9 колонками
  таблице было тесно даже после сокращения текста в шапке; переключили на
  альбомную по прямой просьбе пользователя (`layout: "landscape"` в
  `PDFDocument`) — при книжной альбомная разница в 250pt ширины решает
  давление на колонки разом, без урезания шрифтов.
- **Шапка** (KitchenDesk + подзаголовок слева, дата формирования и число
  позиций справа), **заголовок отчёта** (название, период, "Сформировано
  ... · N позиций") — один раз в начале документа, не повторяется на
  каждой странице (в отличие от шапки самой таблицы, которая повторяется).
- **Таблица**: № / Фото / Наименование / Категория / Было / Приход /
  Списание / Стало / Примечание. Доли колонок по ТЗ (§7) не подошли
  буквально — измерение через `doc.widthOfString()` показало, что
  "ПРИМЕЧАНИЕ" и "СПИСАНИЕ" bold 7pt не помещаются в рекомендованные 9%/8%
  и переносятся на вторую строку, наезжая на линию под шапкой (тот же
  класс бага, что уже чинили в первой версии этого экспорта). Финальные
  доли, после ещё одной правки по живому скриншоту (числовые колонки были
  с запасом шире нужного — сузили, отдали освободившееся "Примечанию"):
  № 6% / Фото 15% / Наименование 19% / Категория 14% / Было 7% / Приход
  7% / Списание 8% / Стало 7% / Примечание 17%.
- **Позиции идут по номеру каталога (1, 2, 3, ...), без группировки по
  категориям** — категория видна отдельной колонкой, но не влияет на
  порядок строк (по прямой просьбе пользователя; в самой первой версии
  этого экспорта сортировка была по категории — убрано).
- **Фото — `object-fit: contain`, центрировано, без рамки**, в бокс
  `photoBoxW × photoBoxH` (сейчас ширина = вся ширина колонки "Фото" за
  вычетом отступов, высота — константа `44pt`, около 15.5мм) — заметно
  больше исходных ~8мм, но НЕ по нижней границе ТЗ (22-28мм): первая
  прикидка на такой высоте укладывала всего 4-5 позиций на лист (227
  позиций растянулись бы куда больше прежних 11 страниц), пользователь
  попросил уменьшить (было 28pt). Затем высоту бокса снова подняли с 28pt
  до 44pt — большинство реальных фото вертикальные, а более низкий и
  широкий бокс обрезал их `fit`'ом по высоте до узкой полоски (contain
  ограничивается меньшей из сторон относительно пропорций фото, ширина
  колонки для портретного фото почти не участвует). Итог — компромисс
  между тремя требованиями (крупное фото / компактные строки / не резать
  вертикальные фото), после двух раундов правок по реальным скриншотам с
  тестовыми данными; при экспорте всех ≈227 позиций итоговая плотность —
  ориентировочно 9 позиций на обычную страницу (без крупной
  шапки-заголовка), то есть около 25 страниц вместо прежних 11 —
  пользователь принял этот компромисс осознанно, зная цену в страницах.
- Нет фото — компактный нейтральный плейсхолдер (светло-серый прямоугольник
  с прочерком), не декоративная иллюстрация.
- Числовые колонки — по центру; "Стало" — полужирным на светло-зелёной
  заливке (`#EEF4EF`) на всю высоту строки, не только под текстом.
  Приход/списание — "—" при нуле, иначе `+N`/`−N` приглушёнными
  зелёным/красным (`#2F6844`/`#B3433B`).
- Высота строки — не фиксированная, а `max()` от бокса фото, названия
  (bold, до 2+ строк без обрезания), категории и примечания — тот же
  принцип, что и в первой версии, просто с новыми размерами.
- Внизу каждой страницы — "KitchenDesk" + "Порядок на кухне — больше
  возможностей" слева, "Страница N из M" справа (единая подпись бренда,
  задел на остальные модули KitchenDesk). После последней позиции —
  блок "ИТОГО ЗА ПЕРИОД" с суммами прихода/списания, с разделителями до и
  после.

**Шрифт — не Inter, как просило ТЗ, а по-прежнему DejaVuSans/-Bold**
(тот же файл, что уже был в проекте). У Inter в репозитории Google Fonts
нет статичных начертаний (`ofl/inter/static/` не существует, только
единый вариативный `Inter[opsz,wght].ttf`), а попытка получить из него
отдельные Regular/Bold через `fontkit.getVariation({wght})` и
зарегистрировать в pdfkit ломается при вставке — `TypeError: First
argument to DataView constructor must be an ArrayBuffer` внутри
`fontkit`'овского `encodeSimple`, воспроизведено отдельным тестовым
скриптом до переделки самого экспорта, не похоже на что-то легко
чинимое поверх сторонних библиотек. ТЗ прямо допускает Arial как
альтернативу — DejaVuSans тот же класс нейтрального sans-serif с полной
поддержкой кириллицы, что уже отработано в проекте.

Подводный камень с футером (остался с первой версии): pdfkit сам
добавляет новую страницу для любого `text()`, оказавшегося ниже
`margins.bottom`, даже с явными координатами — футер рисуется ЗА нижним
полем (в самом низу листа). Лечится временным обнулением
`doc.page.margins.bottom` на время отрисовки футера (и `lineBreak:
false`). Тот же класс бага задел и новый блок "ИТОГО ЗА ПЕРИОД" — проверка
"хватит ли места" перед ним сначала резервировала меньше места, чем блок
реально занимает (76pt вместо зарезервированных ~57pt), из-за чего он мог
наехать на футер, если начинался у самого низа страницы — поправлено
(запас увеличен до 90pt).

## Шаги деплоя

### 1. Backend

Скопировать `backend/oko-inventory-api.js`, `backend/oko-inventory-
store.js`, `backend/oko-inventory-telegram.js` и `backend/oko-known-
chats.js` в папку существующего бэкенда (туда же, где `bot.js` и файлы
`oko-order-relay`).

**Если `oko-order-relay` уже задеплоен** — там уже есть свой `oko-known-
chats.js`, тот же самый файл. Копия отсюда его просто перезапишет (файл
идентичный, ничего не потеряется) — это нормально, оба модуля читают один
и тот же `data/oko-known-chats.json`, общий список групп/тем.

Поставить зависимость (если её ещё нет в проекте):
```
npm install exceljs
```

В `.env` бэкенда — отдельная переменная не нужна, инструмент использует
тот же `OKO_ADMIN_PASSWORD`, что и `oko-order-relay` (если её там ещё нет —
завести).

В точке входа бэкенда (та же точка, где монтируется `oko-order-relay`)
подключить:
```js
const { createOkoInventoryRouter, createOkoInventoryCountRouter, registerInventoryDraftListener } = require("./oko-inventory-api");
app.use("/api/oko-inventory", createOkoInventoryRouter(bot));
app.use("/api/oko-inventory-count", createOkoInventoryCountRouter());
app.get("/count/:token", (req, res) => res.sendFile(path.join(<ПУТЬ_ДО_FRONTEND>, "inventory/count/index.html")));
registerInventoryDraftListener(bot);
```
В отличие от прошлой версии, `createOkoInventoryRouter` теперь **принимает
`bot`** — нужен, чтобы отвечать в тему списаний («Принято в обработку»,
«✅ Записано: ...»).

**Новое: `createOkoInventoryCountRouter()` и маршрут `/count/:token`** —
для страницы повара (см. «Пересчёт утвари» выше). Это НЕ статика через
`express.static` — нужен именно серверный маршрут с параметром, который на
любой токен отдаёт один и тот же `frontend/count/index.html` (токен из
`req.params.token` внутри страницы не участвует, весь разбор — на
клиенте через `location.pathname`, дальше страница сама стучится в API по
этому токену). Если это пропустить — ссылка на пересчёт будет вести на
404, и сама админка при этом будет выглядеть рабочей (тот же класс
проблемы, что и с пропущенным `bot` раньше — не видно по фронтенду
админки, что что-то не подключено).

**Про `registerChatDiscovery(bot)` / `registerIdCommand(bot)`** (из
`oko-known-chats.js`) — если `oko-order-relay` уже вызывает их в этой же
точке входа, **повторно вызывать не нужно** (иначе `/okoid` ответит дважды
на одно сообщение). Если `oko-order-relay` не задеплоен и `oko-inventory` —
первый модуль, который использует `oko-known-chats.js`, вызвать их здесь:
```js
const { registerChatDiscovery, registerIdCommand } = require("./oko-known-chats");
registerChatDiscovery(bot);
registerIdCommand(bot);
```

Перезапустить процесс через pm2.

### 2. Frontend (статика, без сборки)

Скопировать файлы так, чтобы получилось:
```
/home/kitchendesk/frontend/inventory/admin/index.html   <- frontend/admin/index.html
/home/kitchendesk/frontend/inventory/count/index.html   <- frontend/count/index.html
```

Отдельный nginx-блок не нужен — путь `/inventory/...` покрывается тем же
общим `location /`, что и `/oko-order/`, `/manual/`, `/web/`. Страница
повара (`/count/<токен>`) раздаётся не отсюда, а серверным маршрутом
бэкенда (см. выше «1. Backend») — она не под `/inventory/...`.

Проверить:
```
curl -I https://kitchendesk.chefplan.ru/inventory/admin/
```
Должно быть 200.

### 3. Первый запуск

Открыть `https://kitchendesk.chefplan.ru/inventory/admin/`, ввести пароль
(`OKO_ADMIN_PASSWORD`). Дальше всё через саму страницу: добавить позиции
(можно сразу с фото и начальным количеством из присланной таблицы),
отмечать приход/списание по мере необходимости, скачивать Excel за нужный
период кнопкой «Скачать таблицу».

В карточке «Настройки Telegram» выбрать (или вписать ID вручную) группу и
тему, куда повара кидают фото со списанием/приходом утвари — после этого
бот начнёт готовить черновики из новых сообщений в этой теме.

### 4. Перенос существующего списка утвари (225 позиций, разово)

Готовый скрипт-импорт — в папке `import/`: `import-inventory.js`,
`inventory-dataset.json` (все 225 строк: название, размер, ед. изм,
примечание, текущее количество — взято из присланного файла) и
`photos/` (223 фото, автоматически сопоставленные каждой строке по
позиции в PDF — 2 позиции, «Шампур для шашлыка» и «Мангал», в исходном
файле были без фото).

```
cp oko-inventory/import/import-inventory.js \
   oko-inventory/import/inventory-dataset.json <BOT_DIR>/
cp -r oko-inventory/import/photos <BOT_DIR>/
cd <BOT_DIR>
node import-inventory.js
```

Скрипт вызывает тот же `addItem()`, что и сама админка — каждая позиция
получает начальный остаток равный «Остатку на конец ИЮЛЯ» из присланной
таблицы (текущее реальное количество), одной движением с причиной
«начальный остаток». Скрипт откажется запускаться, если каталог уже не
пустой (защита от случайного повторного импорта) — `--force` обходит
эту проверку, если нужно осознанно добавить позиции поверх существующих.

**Позиция №102** в исходном файле была без названия (только фото и
количество) — импортирована как «Без названия (уточнить)», стоит зайти
в админку и переименовать во что-то осмысленное, когда будет понятно,
что это за предмет.

Проверено локально перед тем как класть в репозиторий: скрипт
запускался на тестовой копии `oko-inventory-store.js`, дал ровно 225
позиций (223 с фото), сумма остатков и содержимое каждой проверены;
повторный запуск без `--force` корректно отказывается запускаться.
Фотографии в PDF сопоставлены с номерами строк автоматически — по
вертикальной позиции на странице; сверено визуально на выборке (№1, 15,
50, 102, 108, 121, 176, 217, 223) — всё совпало.

## Проверено локально перед деплоем

Роутер и хранилище прогнаны на тестовом сервере (не на боевом): создание
позиции с начальным остатком → сохраняется как первое движение; приход и
списание меняют остаток корректно (проверено арифметически); фото
сохраняется отдельным файлом и раздаётся с паролем; экспорт отдаёт
настоящий `.xlsx` с правильными колонками, суммами по периоду и встроенной
картинкой (проверено распаковкой файла — валидный `xl/media/`+`xl/drawings/`).
Фронтенд проверен визуально (добавление позиции, приход, история, остаток
обновляется на странице без перезагрузки).

**Черновики из Telegram** (добавлено позже, отдельная проверка) — прогнано
на тестовом сервере с поддельным `bot` (без реального Telegram): фото не из
настроенной темы игнорируется; фото из настроенной темы с подписью «разбили
2 тарелки» — верно определило тип (списание), количество (2), позицию
(«Тарелка обеденная», уже была в каталоге), скачало и сохранило фото
байт-в-байт; бот-ответ в тему («Принято в обработку...») ушёл с правильным
текстом и `reply_to_message_id`/`message_thread_id`. Подтверждение
черновика через `/drafts/:id/confirm` создало движение с тем же фото и
корректно уменьшило остаток (20 → 18), черновик пропал из списка
ожидающих, в тему ушло «✅ Записано: ...». Отклонение черновика убирает его
из списка, остаток не трогает. Подпись без слов-подсказок («купили новую
сковородку») и позиции, которой ещё нет в каталоге, — черновик всё равно
создаётся, просто без угаданной позиции (дозаполняется вручную). Сообщение
без фото в той же теме — игнорируется, черновик не создаётся. Выпадающий
список «Настройки Telegram» проверен с непустым `oko-known-chats.json` —
показывает группу/тему по названию и верно подставляет уже сохранённые
Chat ID/Thread ID.

**Категории** — прогнано на тестовом сервере: создание категории → сразу
в списке и в выпадающем списке позиций; назначение категории позиции через
инлайн-селект в строке → сохраняется, фильтр по этой категории в «Позиции»
показывает только её; удаление категории → позиции остаются в каталоге
с остатками и историей, просто `categoryId` становится `null`, фильтр
«Без категории» их находит. Проверено визуально (скриншот) — карточка
«Категории», чипы фильтра, поле категории в форме добавления и инлайн-выбор
в каждой строке.

**Черновики v2 (кандидаты с %, степпер, создание позиции)** — прогнано на
тестовом сервере: подпись «разбили тарелку 2» при двух похожих позициях
(«Тарелка обеденная», «Тарелка глубокая») дала оба варианта по 86% — клик
по второму варианту верно переключает и подсветку чипа, и выбор в
выпадающем списке; степпер +/- на одном черновике не трогает количество
другого (проверена изоляция состояния между карточками); превью «Было →
Станет» верно пересчиталось при выборе позиции и типа. Подпись «пришла
новая сковородка 5» (позиции нет в каталоге) — кандидатов ноль, кнопка
«Создать новую позицию» открыла форму с подсказкой названия «Новая
сковородка» (без огрызков слов после чистки — было исправлено при
проверке), создание позиции переиспользовало уже скачанное фото черновика
(`hasPhoto: true` у новой позиции без повторной загрузки) и сразу
подставило её в выбор. Проверено визуально (скриншот).

**Вкладки/боковая панель** — прогнано на ширине 1280px (ПК): вход всегда
открывает «Входящие», клик по каждому пункту меню переключает активную
вкладку и подсвечивает пункт, бейдж счётчика черновиков в самом меню
работает. Проверено и на ширине 390px (мобильный) — боковая панель
превращается в горизонтальную полосу вкладок сверху, реального
горизонтального скролла страницы не появляется (проверено через
`scrollWidth`/`clientWidth`). Скриншоты всех 4 вкладок на ПК и мобильного
вида — приложены в чате.

**Модальные окна + мобильный гамбургер** (после отзыва пользователя,
следующая правка) — карточка «Экспорт» на вкладке «Настройки» убрана
совсем (не задублирована), кнопки «+ Добавить позицию»/«📥 Экспорт» теперь
наверху вкладки «Позиции», открывают модальные окна с тем же содержимым;
крестик и клик по фону корректно закрывают оба окна (проверено через
Playwright), успешное добавление позиции закрывает окно само и сразу видно
новую позицию в списке. Мобильная навигация (390px) — боковая панель
скрыта, вместо неё верхняя панель с кнопкой-гамбургером, открывающей
выдвижную панель справа с теми же 4 пунктами и бейджем; клик по пункту
одновременно переключает вкладку и закрывает панель (проверено). Скриншоты
закрытого/открытого гамбургер-меню и обеих модалок — приложены в чате.

**Оформление сообщений бота** — все три сообщения (подключение темы,
"принято в обработку", "записано") переведены на Markdown-разметку
(`parse_mode: "Markdown"`, жирные значения, разделитель `━━━━━━━━━━━━━━`,
эмодзи ➕/➖ для типа движения), тот же стиль, что уже используется в
oko-waiter-guide для отзывов. Название позиции экранируется той же
функцией `escapeMd`, что и там — спецсимволы Markdown (`_`, `*`, `` ` ``,
`[`) в названии, если админ их случайно ввёл, не ломают форматирование
сообщения. Проверено на тестовом сервере: все три сообщения (текст+
`parse_mode`) сверены дословно, включая позицию с названием, специально
содержащим `_` и `*` — экранирование сработало корректно.

**Редактирование вместо нового сообщения** (следующая правка, по отзыву
пользователя) — строка "Подтвердите в админке инвентаризации." убрана из
"Принято в обработку" (излишняя). id отправленного сообщения теперь
сохраняется на черновике (`botReplyMessageId`); при подтверждении в
админке вызывается `bot.editMessageText` с этим id вместо `sendMessage` —
то же сообщение в теме меняет текст на "Записано" вместо появления
второго. Проверено на тестовом сервере с доработанным поддельным ботом
(умеет и `sendMessage`, и `editMessageText`, эмулирует правку по
`message_id`): после подтверждения в теме по-прежнему ровно 2 сообщения
(было отправлено 2, а не 3), и то самое сообщение №2 помечено `edited:
true` с новым текстом "✅ Записано" — прежний текст "Принято в обработку"
не сохранился отдельной записью, как и должно быть при настоящем
редактировании.

**Дата движения — от черновика, не от подтверждения** (следующая правка,
по вопросу пользователя про историю/экспорт) — прогнано на тестовом
сервере: черновик создан "сегодня", вручную состарен на 7 дней назад
(`createdAt` в `data/oko-inventory-drafts.json` сдвинут на 7 дней в
прошлое, имитируя владельца, который подтверждает не сразу), подтверждён
"сегодня" через API — в ответе `movement.date` оказалась именно та дата

**Баг: пропадали фото после любого действия, требующего перерисовки**
(пользователь заметил после смены категории, но баг задевал и черновики) —
`loadPhoto`/`loadDraftPhoto` кэшируют скачанный blob по id
(`photoUrls`/`draftPhotoUrls`), чтобы не качать фото повторно — но
`render()`/`renderDrafts()` пересоздают `<img>` заново через `innerHTML`
при КАЖДОМ действии (смена категории, приход/списание, поиск, фильтр,
степпер количества у черновика, выбор кандидата и т.д.) — новый `<img>`
без `src`. Старый код при наличии кэша делал ранний `return`, ни разу не
проставляя `src` на новый элемент — фото визуально пропадало (файл на
диске никуда не девался, помогала только полная перезагрузка страницы,
которая обнуляла сам кэш). Поправлено: сначала находим `<img>` в DOM,
если blob уже в кэше — сразу проставляем `src` из кэша (без сети), иначе
качаем один раз и тоже проставляем. Проверено на тестовом сервере через
Playwright: позиция с реальным фото, смена категории через инлайн-селект
→ `src` фото остался тем же валидным `blob:` URL до и после (не пропало),
подтверждено и скриншотом.
