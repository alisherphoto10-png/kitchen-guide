# Print Agent — оперативный контекст (читать новой сессии в первую очередь)

Этот файл — не техническая документация (она в других местах, ссылки в
конце), а введение в контекст: чтобы любая новая сессия Claude — что эта,
работающая в репозитории `kitchen-guide`, что "та, другая", с доступом к
серверу — за один файл поняла, что вообще происходит, и не заставляла
пользователя пересказывать всё заново.

## Что это вообще такое

В заведении есть настоящий термопринтер (Enter.CO SX-82V), подключённый по
локальной сети к моноблоку (Windows). Бэкенд KitchenDesk — в облаке и до
принтера в локальной сети заведения физически не достаёт. Решение —
локальный агент, `oko-shelf-life/agent/print-agent.js`: работает прямо на
моноблоке, постоянно в фоне (без окна на экране), раз в несколько секунд
спрашивает у облачного бэкенда "есть что печатать?" и сам шлёт байты
принтеру по сети (ESC/POS, порт 9100).

## Архитектурный принцип: "тупой агент, умный сервер"

Содержимое чеков (что и в каком порядке печатать) собирается ЦЕЛИКОМ на
сервере — агент просто берёт присланные строки (`job.printLines`) и
опциональный QR (`job.qrData`) и кодирует их в байты для конкретного
принтера. Агент отвечает только за физику печати (кодировка кириллицы,
отступы, форматирование, QR-команда) — не за то, ЧТО написано на чеке. Так
почти любая правка содержимого чеков — это правка сервера, без единого
прикосновения к моноблоку.

С 2026-09-20 то же самое верно и для КОДА самого агента: он умеет
самообновляться (см. ниже) — значит теперь и правки формата/логики агента
тоже не требуют физического похода к моноблоку, кроме самого первого раза.

## Реальные факты о деплое (легко перепутать, уже путались)

- Основной бэкенд KitchenDesk (план/чек-лист/смена) — на сервере это
  `/root/kitchendesk/backend`, единый процесс, pm2-имя `kitchendesk`, порт
  3004, домен `kitchendesk.chefplan.ru`.
- `kitchen2026.chefplan.ru` (порт 3001, процесс `oko-kitchen`) — это
  ОСТАНОВЛЕННЫЙ дубликат-легаси, НЕ второй сервер. Изначально фича печати
  чек-листа планировалась как межсерверный вызов backend → backend именно
  потому что предполагалось два разных сервера — по факту это оказался
  один процесс, см. `oko-checklist-print/README.md`.
- Очередь печати (`oko-shelf-life-print`, роуты `/api/oko-shelf-life-print/
  *`) живёт в ТОМ ЖЕ процессе `kitchendesk`. Значит вызовы "поставить
  задание на печать" из другой части главного бэкенда (например, при
  сохранении плана) — просто вызов функции внутри процесса, никакого HTTP
  между серверами не нужно.
- Реальный принтер: Enter.CO SX-82V, IP `192.168.0.122`, порт 9100,
  кодовая страница CP866 = номер 17 (подобрано эмпирически на реальном
  железе через `node print-agent.js --codepage-test`, для другого принтера
  может быть другой номер).

## Текущая версия агента

Смотреть `AGENT_VERSION` в начале `oko-shelf-life/agent/print-agent.js` —
на 2026-09-20 (последняя правка) это `"2026-09-20.4"`.

## Что уже сделано (коротко и по порядку; подробности — в README модулей)

1. Базовая печать этикеток разморозки/заморозки — справочник сроков
   хранения заготовок, `oko-shelf-life`.
2. Поддержка QR-кода в ESC/POS (`GS ( k`) — сделано заранее, впрок, для
   будущей фичи чек-листа (см. п.9).
3. Дизайн чека собирается целиком на сервере (`buildPrintLines` и т.п.) —
   агент просто печатает присланные строки, ничего не сочиняет сам.
4. Автозагрузка на Windows без видимого окна консоли (`.vbs`,
   `WshShell.Run(...,0,False)`) — решает "агент не запущен после
   перезагрузки, а окно консоли на экране никто не хочет видеть".
5. Чек-подтверждение при каждом старте агента — физическое доказательство
   "агент жив", раз окна на экране не видно и в логи не заглянешь.
6. Отступ перед обрезкой бумаги увеличен (было 3 пустые строки — резало
   слишком близко к тексту/QR, неудобно было взять чек в руки; стало 8).
7. Самообновление — агент сам, при каждом старте и раз в 6 часов, сверяет
   свою версию (`AGENT_VERSION`) с версией на сервере (роуты
   `/api/oko-shelf-life-print/agent-version` и `/agent-latest`, тот же
   `X-Agent-Token`, что и у остальных агентских роутов). Если на сервере
   новее — скачивает код, переписывает СЕБЯ (`fs.writeFileSync(__filename,
   ...)`), перезапускается. Местные настройки (`agent-config.json` —
   реальный токен, IP принтера, отступ перед обрезкой) — отдельный файл
   рядом, самообновление код его не трогает. Перед перезапуском печатает
   чек "Агент обновлён / Версия: ...".
8. Шапка "KitchenDesk" на любом чеке — жирным, по центру, крупнее
   (`ESC a 1` / `ESC E 1` / `GS ! 1`) — срабатывает автоматически, если
   первая строка `printLines` дословно `"KitchenDesk"`, остальной текст не
   затронут.
9. Фича "печать чек-листа смены при сохранении плана + завершение сканом
   QR" (`oko-checklist-print/README.md`) — использует ЭТОТ ЖЕ агент без
   единой правки: генерическая поддержка произвольных `printLines`/
   `qrData` в очереди печати была добавлена заранее именно ради этого.
10. Разведка второго принтера (Xprinter XP-235B, по USB, для этикеток со
    штрихкодом) — агент один раз выполняет `wmic printer get ...` и шлёт
    сырой результат на сервер (`POST /agent-report`), не заставляя
    пользователя работать с командной строкой самому. Ждём результата (см.
    "Открытые вопросы" ниже).
11. Печать тикета заказа (`oko-order-relay/README.md`) — при отправке
    заказа через форму (заведения "Облако"/"Мясо") печатается бумажный
    тикет, той же очередью/агентом, никакого дублирования. Требует
    проверки реального пути до `oko-shelf-life-store.js` при деплое (файл
    `oko-order-api.js` копируется в другое место бэкенда, не туда же, где
    чек-лист).
12. Страница настроек чекового принтера (`http://localhost:3500`, только
    на самом моноблоке) — агент сам поднимает обычную веб-страницу
    (встроенный `http`, без фреймворков): IP/порт принтера, кодовая
    страница, отступ перед обрезкой, оформление шапки "KitchenDesk" (три
    независимых флага, раньше были зашиты намертво). Сохранение применяется
    сразу, без перезапуска. Плюс кнопки "Тестовая печать"/"Тест кодовых
    страниц" — сразу видно результат. Первый шаг к "полноценному
    приложению", о котором просил пользователь — начали с чекового
    принтера, т.к. по нему уже всё известно; для этикеточного такая же
    страница имеет смысл после разведки (см. п.10) и выбора протокола.
13. Многозаведенческая печать — очередь и агентский токен теперь привязаны
    к заведению (не один общий секрет на всех), у каждого заведения свой
    список принтеров (несколько станций на кухне поддерживаются —
    `printerTarget` на задании, сервер сам решает, куда слать). Управляется
    веб-панелью `/print-admin/` (`oko-shelf-life/frontend/
    restaurants-admin/index.html`) — заведения добавляются, токены
    выпускаются и принтеры настраиваются оттуда, без правки сервера или
    переноса файлов на конкретный моноблок. Легаси-заведение (ОКО) не
    трогали — старый `OKO_SHELF_LIFE_AGENT_TOKEN` продолжает работать как
    раньше. Агент печатает туда, куда скажет сервер в задании
    (`job.printerIp`/`printerPort`); свой локальный `PRINTER_IP` остаётся
    только как "тестовый принтер" для кнопок настройки и запасной вариант
    для легаси-заведения. `oko-order-relay` подключён (`restaurantId:
    order.venue`); чек-листу (`oko-checklist-print`) это ещё нужно
    прокинуть отдельно — см. "Открытые вопросы" в его README.
    **Найден и исправлен реальный баг вскоре после первого деплоя:**
    задание для ещё не заведённого в панели `restaurantId` становилось
    невидимым ни для одного токена (не "падало в легаси", как ошибочно
    предполагал первый деплой) — несколько минут реальные тикеты заказов
    терялись, поймали на живом сервере и откатили. Исправлено в сторе
    (`resolveRestaurantId()` перед сохранением любого задания — см.
    `oko-shelf-life/README.md`), не откатом строки в `oko-order-relay`.
14. Синхронизация списка заведений с настоящим реестром KitchenDesk
    (2026-09-20) — панель `/print-admin/` до этого сама была источником
    истины (заведение заводилось вводом названия в форме), что могло
    разойтись с реальными клиентами KitchenDesk. Пользователь явно
    потребовал синхронности: "В print агенте не должно быть других
    заведений, которые нету, которые не подключены к kitchen desk." Теперь
    список заведений в панели **читается напрямую из настоящей таблицы
    `restaurants`** (тот же процесс, `store.listKitchenDeskTenants()`,
    только активные — `deleted_at IS NULL`), панель только "включает"
    печать для существующего заведения (создаёт токен + список принтеров),
    завести несуществующее заведение больше нельзя. Print-agent остался
    отдельным модулем — таблицу заведений только читает, не пишет в неё и
    не владеет ей ("ничего внедрять не будем, это как новый модуль будет
    отдельный" — пользователь). Заодно легаси-заведение ОКО (раньше жило
    отдельной веткой по совпадению токена с переменной окружения, без
    записи в списке заведений вообще) переведено на эту же схему — стало
    обычной записью с реальным id (`1`, как в таблице `restaurants`),
    токен при миграции явно задан тем же значением, что уже в
    `OKO_SHELF_LIFE_AGENT_TOKEN`, чтобы уже работающий на моноблоке агент
    не пришлось переконфигурировать. Подробности и точная команда миграции
    — `oko-shelf-life/README.md`, раздел "Почему список заведений не
    вводится руками". **Задеплоено и подтверждено (2026-09-20):** путь до
    db-модуля основного бэкенда оказался не `../db/postgres`, а
    `./db/postgres` (`oko-shelf-life-store.js` лежит в `backend/src/`,
    рядом с `db/`, а не на уровень выше) — поправлено при деплое; миграция
    ОКО (`POST /restaurants/1/enable`) выполнена, `enabled: true`, легаси-
    токен продолжает работать без изменений на моноблоке, IP/порт принтера
    теперь приходят в задании от сервера. Демо-заведение (id 6) оставлено
    выключенным.
15. Скачивание готового `agent-config.json` из панели (2026-09-20) — до
    этого токен для нового заведения приходилось передавать текстом и
    вписывать в файл на моноблоке руками. Кнопка "⭳ Скачать файл настроек
    агента" на карточке включённого заведения отдаёт файл с уже
    подставленными `BACKEND_URL`/`AGENT_TOKEN` (и IP/портом первого
    принтера, если он уже добавлен в панели) — просто положить рядом с
    `print-agent.js` на моноблоке, агент подхватит сам при первом запуске.
    См. `oko-shelf-life/README.md`, п.4 в разделе "Заведения и принтеры".
16. Однокликовый запуск + PDF-инструкция для установщика на месте
    (2026-09-21) — выяснилось в разговоре с пользователем, что "три файла
    в папку, дальше руками команды в cmd" — не сценарий для человека без
    технических навыков, который физически подключает принтер в
    заведении. Добавлен `agent/start-agent.bat` — общий для всех
    заведений файл-лаунчер (не привязан к пути установки, `cd /d
    "%~dp0"`), двойной клик по которому одним действием прогоняет
    `node print-agent.js --install-autostart` и сразу запускает агента
    без окна. Итоговый комплект для установки — **три файла**:
    `print-agent.js` + `start-agent.bat` (оба общие, не меняются от
    заведения к заведению) + персональный `agent-config.json` (см. п.15).
    Плюс отдельный PDF `print-agent/docs/kitchendesk-chekovyi-printer-
    instrukciya.pdf` — пошаговая инструкция для не-технического человека
    на месте, со словарём терминов и реальными скриншотами панели и
    страницы настроек агента (не макеты). Только про чековый принтер.

## Открытые вопросы / что в работе

- **Второй принтер (Xprinter XP-235B, USB, этикетки со штрихкодом)** —
  разведка (см. п.10) задеплоена, но ещё не подтверждена на реальном
  железе (пользователь включит моноблок во вторник). Дальше, по отчёту
  (`GET /agent-reports`), нужно будет: понять протокол принтера (скорее
  всего TSPL, не ESC/POS — другой язык команд, чем у чекового), и способ
  отправки байтов на локальный принтер по USB из Node без npm-пакетов
  (вероятно — через `copy /b` на назначенный Windows порт, дело ещё не
  решено окончательно).

## Как теперь вносить изменения в агента

1. Править `oko-shelf-life/agent/print-agent.js` в этом репозитории
   (ветка `claude/oko-waiter-guide-xlsx`) — обязательно поднять
   `AGENT_VERSION` на новое значение.
2. Коммит и пуш в ту же ветку.
3. Передать в сессию с доступом к серверу задачу на деплой: обновить на
   сервере `oko-shelf-life/agent/print-agent.js` (и
   `oko-shelf-life/backend/oko-shelf-life-api.js`, если он тоже менялся),
   перезапустить процесс `kitchendesk`.
4. Агент на моноблоке подхватит новую версию сам — при следующем
   запуске/перезагрузке моноблока, либо в течение 6 часов автоматически.
   Пользователю вручную скачивать и переносить файл больше не нужно
   (кроме самого первого раза, когда механизм самообновления только
   появился).

## Кому и зачем этот файл

Пользователь ведёт эту работу через две параллельные сессии Claude: одну
без доступа к серверу (пишет и тестирует код локально, координирует), и
другую — с реальным доступом к серверу, которая деплоит. Обе сессии не
помнят предыдущих разговоров друг друга. Этот файл — общая точка входа
для любой из них (или следующей, если эти тоже закончатся), чтобы не
начинать каждый раз с нуля.
