# KitchenDesk API для бота технолога

Ваш бот сам забирает у KitchenDesk две вещи — без Telegram и без пересылок:

1. **Приходные накладные** — что пришло от закупщика: товар, сколько заказали, сколько приняли, кто принял и подписал.
2. **Файлы цен закупщика** — те самые `ОКО 17.10.xlsx`, которые закупщик кидает в группу закупа. KitchenDesk сохраняет их у себя, бот скачивает.

Всё только для чтения и только по вашему заведению.

---

## 1. Адрес и ключ

Адрес: `https://kitchendesk.chefplan.ru/api/ext`

Ключ выдаёт владелец KitchenDesk (панель суперадмина → заведение → «Интеграции» → «API для внешних систем»). Выглядит так: `kdx_7Qm2VxL9pR4tNw8sKc1ZyHf6JdA3bGe5uTo0iXqWlMn`. Ключ показывается один раз — сохраните его в настройках бота (переменная окружения, не в коде). Если ключ утёк — попросите отозвать и выдать новый.

Ключ передаётся в каждом запросе заголовком:

```
Authorization: Bearer kdx_…
```

Проверить, что ключ работает:

```bash
curl -s https://kitchendesk.chefplan.ru/api/ext/ping -H "Authorization: Bearer $KD_KEY"
```

```json
{ "ok": true, "restaurant": { "id": 1, "name": "ОКО" }, "key": "Бот технолога" }
```

## 2. Как забирать «только новое» — since и next_since

Оба списка (накладные и файлы) работают одинаково:

1. Первый раз запросите с датой, с которой нужны данные: `?since=2026-10-01`.
2. В ответе есть `next_since` — **сохраните его** (в файл/базу бота).
3. В следующий раз передайте его: `?since=<сохранённый next_since>`. Придёт только то, что появилось или изменилось после прошлого раза.
4. Если `has_more: true` — данных больше, чем в одном ответе (по умолчанию 50, максимум `limit=100`). Сразу запросите ещё раз с новым `next_since`, пока `has_more` не станет `false`.

Запрашивать можно как угодно редко — раз в час, раз в день, раз в 4 дня. Ничего не потеряется: всё накопленное придёт пачкой.

**Одна и та же накладная может прийти повторно** — если её исправили или оформили по ней возврат. Поэтому сохраняйте накладные **по `id`, заменяя старую версию** новой, а не добавляя дубль.

```bash
curl -s "https://kitchendesk.chefplan.ru/api/ext/receipts?since=2026-10-01" -H "Authorization: Bearer $KD_KEY"
```

### Поля накладной

| Поле | Что это |
|---|---|
| `id` | постоянный номер накладной в KitchenDesk — по нему сохранять/заменять |
| `number` | номер документа «ПН-0001» |
| `status` | `posted` — проведена. `reopened` — её открыли на исправление: данные устарели, ждите, она придёт снова уже `posted` |
| `delivery_day` | **«закуп на» — день, когда закупщик закупил и привёз. Файл цен `ОКО 17.10.xlsx` относится именно к этому дню** |
| `delivery_date` | то же, как строка «17.10.2026» |
| `order_date` | день, когда кухня составила список закупа (обычно накануне `delivery_day`) |
| `seq`, `backorder_of` | довоз: если в первый раз привезли не всё, остаток довозят отдельной накладной (`seq` 2, 3…, `backorder_of` — ссылка на первую). Довоз часто приходит с тем же `delivery_day` |
| `supplier` | поставщик |
| `posted_by`, `posted_at` | кто и когда провёл |
| `supplier_refused_to_sign`, `supplier_refuse_reason` | закупщик не подписал и почему |
| `signatures` | подписи: `side` = `kitchen` (кухня), `supplier` (закупщик), `bar` (бар подтвердил свою часть); `name` — кто |
| `changed_at` | когда накладная последний раз менялась (для курсора) |

### Поля позиции (`items`)

| Поле | Что это |
|---|---|
| `product_name`, `unit` | товар и единица строки, как в заказе. У заведения с iiko название — буквально как в номенклатуре iiko (после сверки каталога) |
| `supplier_note` | приписка: фасовка или марка («480 гр»). Название при этом то же, что в iiko: «трюфельная паста» 480 гр и 540 гр — две строки с одним `iiko.product_id` и разной `supplier_note`. Нет приписки — `null` |
| `purpose` | для какого отдела: `kitchen` кухня, `bar` бар, `hall` зал, `household` хоз. товар |
| `ordered_qty` | сколько заказали (число; `null`, если в заказе было написано не числом — тогда смотрите `ordered_raw`) |
| `received_qty` | сколько фактически приняли (в `unit`) |
| `receive_unit`, `received_count` | если товар заказывают штуками, а принимают весом: `received_qty` — вес в `receive_unit` (кг), `received_count` — штуки |
| `returned_qty` | сколько вернули поставщику по возвратам (ВЗ) |
| **`accepted_qty`** | **итого осталось у заведения = принято − возвращено. Для расчёта себестоимости берите это поле** |
| `extra` | привезли сверх заказа (не было в списке) |
| `backorder` | не привезли — довезут позже (придёт отдельной накладной-довозом) |
| `closed_reason` | не привезли и не будет — причина |
| `note` | комментарий принимавшего |
| `checked_by` | кто отметил позицию |
| **`iiko`** | **связь с iiko** (у заведения без iiko — `null`). `status`: `linked` — товар iiko, `product_id` — его id в iiko, `catalog_unit` — единица iiko (может отличаться от `unit`: строку иногда заказывают в другой единице, например манго весом); `not_in_iiko` — **новый товар, его ещё нет в iiko: заведите его** (`note` — готовый текст); `own` — свой товар заведения, в iiko не ведётся (например, кофемолка); `unchecked` — карточку ещё не сверили с iiko; `no_card` — строка без карточки каталога. Статус и id — у каждой строки свои: лайм для кухни и лайм для бара — две строки (разные склады) с одним `product_id` |

### Возвраты (`returns`)

Если часть товара вернули поставщику, в накладной появляется возврат «ВЗ-0001» с позициями (`receipt_item_id`, `product_name`, `supplier_note`, `qty`, `reason`). Название и приписка — так же, как в позициях накладной: раздельно. `returned_qty`/`accepted_qty` в позициях уже посчитаны с учётом действующих возвратов. Отменённый возврат помечен `voided: true` и в расчёт не входит.

## 4. Файлы цен закупщика

Когда закупщик присылает в группу закупа файл (`ОКО 17.10.xlsx`), KitchenDesk сохраняет его и определяет **день**:
- из названия файла (`ОКО 17.10` → 17.10);
- если в названии даты нет — из первой строки файла («ЗАКУП ОКО 17.10.2026г.»);
- если и там нет — бот KitchenDesk переспрашивает закупщика в группе, и день проставляется по его ответу (файл тогда придёт в ленте ещё раз, уже с днём).

```bash
curl -s "https://kitchendesk.chefplan.ru/api/ext/price-files?since=2026-10-01" -H "Authorization: Bearer $KD_KEY"
```

```json
{
  "items": [
    {
      "id": 13,
      "file_name": "ОКО 17.10.xlsx",
      "day": "2026-10-17",
      "day_source": "name",
      "name_date": "2026-10-17",
      "content_date": "2026-10-17",
      "latest_for_day": true,
      "sent_at": "2026-10-20T09:57:04.000Z",
      "sender_name": "Анвар",
      "size": 6453,
      "mime": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
      "sha256": "53cee037734a6fae111c51f4264c82b84e454b56283594a0920c2680dbfd902d",
      "changed_at": "2026-10-20T09:57:04.462082Z",
      "download_url": "/api/ext/price-files/13/download"
    }
  ],
  "next_since": "2026-10-20T09:57:04.462082Z",
  "has_more": false
}
```

| Поле | Что это |
|---|---|
| `day` | к какому дню закупа относится файл. `null` — день пока не определён, пропустите файл, он придёт снова, когда день проставят |
| `day_source` | откуда день: `name` название, `content` первая строка файла, `reply` закупщик ответил в группе |
| `name_date`, `content_date` | дата из названия и из файла по отдельности (если различаются — KitchenDesk предупредил закупщика; главная — из названия) |
| `latest_for_day` | закупщик мог прислать исправленный файл за тот же день. `true` — это самый свежий файл за этот `day`, берите его |
| `download_url` | скачать сам файл (с тем же ключом) |
| `sha256` | контрольная сумма — если уже скачивали файл с такой суммой, можно не качать |

Скачать файл:

```bash
curl -s -o "ОКО 17.10.xlsx" "https://kitchendesk.chefplan.ru/api/ext/price-files/13/download" -H "Authorization: Bearer $KD_KEY"
```

В файле нужен только первый лист (разделы «Бар» и «Кухня»: наименование, ед. изм., факт. кол-во, цена, сумма). Второй лист — личный учёт закупщика, его не трогать.

## 5. Как сопоставить цены с приёмкой

**Файл цен за день = все накладные с `delivery_day` этого дня.**

```
для каждого файла, где latest_for_day = true и day != null:
    накладные = все накладные, где delivery_day == file.day и status == "posted"
    (обычно одна; если был довоз — несколько, сложите accepted_qty одинаковых товаров)
    сопоставьте строки файла с позициями по названию товара и разделу (Бар ↔ purpose "bar", Кухня ↔ остальное)
```

Закупщик присылает файлы не каждый день — бывает раз в 3–4 дня, но **каждый файл — ровно за один день**. Если пропущено несколько дней, придёт несколько файлов, каждый со своим `day`. Если файл за день уже есть, а накладной с таким `delivery_day` ещё нет (приёмку не провели) — отложите файл и проверьте позже.

Названия товаров в файле закупщика и в KitchenDesk пишутся людьми и могут немного отличаться («Лайм» / «лайм», «Сливки 33%» / «Сливки 33 %») — сравнивайте без учёта регистра и лишних пробелов.

## 6. Ошибки

| Код | Что значит | Что делать |
|---|---|---|
| 401 | нет ключа, ключ неверный или отозван | проверить заголовок; если отозван — попросить новый |
| 400 | неправильный `since` | дата `2026-10-17` или ровно то, что пришло в `next_since` |
| 404 | нет такой накладной/файла (или она чужая, или ещё не проведена) | — |
| 429 | больше 60 запросов в минуту | подождать минуту (заголовок `Retry-After`) |
| 500 | ошибка на стороне KitchenDesk | повторить позже; если повторяется — написать в поддержку KitchenDesk |

Текст ошибки всегда в поле `error`: `{ "error": "Ключ не действует (отозван или неверный)" }`.

## Время и числа

- Все время — в UTC (`Z` на конце). Ташкент = UTC+5.
- Дни (`delivery_day`, `order_date`, `day`) — без времени, `ГГГГ-ММ-ДД`, по Ташкенту.
- Количества — числа с точкой (`2.9`), до 3 знаков после запятой.
