# OKO Shelf Life — справочник сроков хранения + печать этикеток

Справочник ПФ (полуфабрикатов/заготовок): название, условия хранения,
срок хранения, примечание — плюс печать этикеток разморозки/заморозки:
повар выбирает заготовку на отдельной странице (без пароля админки),
жмёт «Разморозил»/«Заморозил», система сама считает дату списания
(текущее время + срок хранения из справочника) и кладёт задание в
очередь. Локальный агент (`agent/print-agent.js`, крутится на
моноблоке заведения — см. ниже, почему не на сервере) забирает задание
и печатает его на чековом принтере по сети (ESC/POS, TCP:9100).

Это временная папка-склад в репозитории `kitchen-guide` — сюда код
попал только для передачи на сервер, как и `oko-inventory/`,
`oko-order-relay/`. После деплоя эту папку из репозитория можно удалить.

## Структура

```
backend/
  oko-shelf-life-api.js     — Express-роутеры:
                                 createOkoShelfLifeRouter()      — items, print-jobs (весь роутер за X-Admin-Password)
                                 createOkoShelfLifePrintRouter()  — items (облегчённо), jobs — для страницы повара и агента (без пароля админки)
  oko-shelf-life-store.js   — файловое хранилище (JSON) + парсер срока хранения в часы + очередь печати
  data/                      — создаётся автоматически при первом запуске
    oko-shelf-life-items.json
    oko-shelf-life-print-jobs.json
frontend/
  admin/index.html           — одна страница: поиск, список, модалка добавить/редактировать/удалить (за паролем)
  print/index.html            — страница повара: выбрал заготовку → выбрал действие → задание на печать (без пароля)
agent/
  print-agent.js              — локальный агент (Node.js, только встроенные модули) — см. "Печать этикеток" ниже
import/
  shelf-life-dataset.json    — 185 позиций из присланного файла "Сроки хранения ПФ.xlsx"
  import-shelf-life.js       — разовый скрипт импорта (тот же приём, что и импорт утвари в oko-inventory)
```

## Данные позиции

```json
{
  "id": "...",
  "number": 1,
  "name": "ПФ Крем ОКО",
  "storageCondition": "0..+4°C, герметичная тара",
  "shelfLifeText": "24 часа",
  "shelfLifeHours": 24,
  "note": "Заварной крем на яично-молочной основе — один из самых скоропортящихся ПФ",
  "archived": false,
  "createdAt": 1234567890
}
```

`shelfLifeText` — как ввёл человек, показывается в админке как есть.
`shelfLifeHours` — распарсенное число часов (для будущего расчёта даты
списания на этикетке: дата разморозки + это число = когда списывать).
Если распознать не удалось — `shelfLifeHours: null`, позиция всё равно
сохраняется, просто без автоматического расчёта (в админке такая
позиция подсвечена оранжевым в колонке «Срок»).

### Баг, пойманный на реальном импорте — родительный падеж "суток"

Первая версия парсера искала стем `"сутк"` (подходит для "сутки",
"сутками") — но **у слова "сутки" родительный падеж множественного
числа неправильный: "суток", а не "сутков"**, и подстроки "сутк" в
слове "суток" нет (с-у-т-**о**-к, а не с-у-т-к). Из 185 реальных позиций
34 не распознались именно из-за этого ("5 суток", "7 суток" и т.д. —
самая частая формулировка в файле). Поправлено на стем `"сут"` (входит
подстрокой во все формы — сутки/суток/сутками); после фикса
распознались все 185.

## Шаги деплоя

### 1. Backend

Скопировать `backend/oko-shelf-life-api.js` и `backend/oko-shelf-life-
store.js` в папку существующего бэкенда (туда же, где `oko-inventory-*`
и `oko-order-relay`).

В `.env` — отдельная переменная не нужна, использует тот же
`OKO_ADMIN_PASSWORD`, что и остальные oko-модули.

В `.env` — добавить `OKO_SHELF_LIFE_AGENT_TOKEN` (любая длинная случайная
строка, придумать самому) — отдельный секрет для локального агента, НЕ
`OKO_ADMIN_PASSWORD`: агент умеет только читать очередь печати и
отмечать задания выполненными, редактировать справочник им не даём.

В точке входа бэкенда подключить:
```js
const { createOkoShelfLifeRouter, createOkoShelfLifePrintRouter } = require("./oko-shelf-life-api");
app.use("/api/oko-shelf-life", createOkoShelfLifeRouter());
app.use("/api/oko-shelf-life-print", createOkoShelfLifePrintRouter());
```

Перезапустить процесс через pm2.

### 2. Frontend (статика, без сборки)

```
/home/kitchendesk/frontend/shelf-life/admin/index.html   <- frontend/admin/index.html
/home/kitchendesk/frontend/shelf-life/print/index.html   <- frontend/print/index.html
```

Отдельный nginx-блок не нужен — покрывается тем же общим `location /`,
что и остальные статические разделы (`/inventory/`, `/oko-order/` и
т.д.).

### 3. Импорт справочника (185 позиций, разово)

```bash
cp oko-shelf-life/import/import-shelf-life.js \
   oko-shelf-life/import/shelf-life-dataset.json <BOT_DIR>/
cd <BOT_DIR>
node import-shelf-life.js
```

Скрипт вызывает тот же `addItem()`, что и сама админка — 185 позиций,
номера 1-185 в том же порядке, что в исходном файле. Откажется
запускаться, если справочник уже не пустой (защита от повторного
импорта) — `--force` обходит эту проверку.

**Важное примечание из исходного файла** (лист «Примечания» в
присланном .xlsx, стоит держать в уме при проверке данных): сроки в
таблице — общие ориентировочные значения по типовой практике
профессиональных кухонь (аналог СанПиН для скоропортящихся ПФ), потому
что в исходных технологических картах поля «Хранение»/«Срок хранения»
не были заполнены. Перед тем как полагаться на них в проде,
рекомендовано: 1) сверить с действующими санитарными нормами
Узбекистана / внутренним HACCP-планом OKO; 2) скорректировать сроки для
позиций с уникальной рецептурой; 3) для сырых мясных/рыбных/молочных ПФ
— придерживаться более строгого срока при сомнении.

### 4. Первый запуск

Открыть `https://kitchendesk.chefplan.ru/shelf-life/admin/`, ввести
пароль (`OKO_ADMIN_PASSWORD`). Дальше — поиск, добавление, правка,
удаление позиций справочника.

## Печать этикеток

**Почему нужен локальный агент, а не печать прямо с сервера.** Бэкенд
KitchenDesk — на удалённом сервере, принтер — в локальной сети
заведения. Сервер физически не достаёт до принтера (тот не в
интернете, за роутером заведения). Поэтому печать идёт в 2 шага:
повар создаёт задание через `POST /api/oko-shelf-life-print/jobs`
(публичный роутер, без пароля), а локальный агент — программа, которая
крутится на моноблоке заведения (Windows, включается/выключается
вместе со сменой) — раз в несколько секунд спрашивает бэкенд
`GET /jobs/pending` (уже со своим секретом, `X-Agent-Token`), и если
есть что печатать — сам открывает сырой TCP-сокет на IP принтера,
порт 9100, и шлёт ESC/POS-команды. После успешной печати сообщает
бэкенду `POST /jobs/:id/done`.

### Протестированное железо

Чековый принтер **Enter.CO SX-82V**: интерфейс USB+LAN, протокол
TCP/IP, порт 9100, команды ESC/POS. Связь по сети подтверждена дважды
— вручную через Android-приложение "ESC/POS Network Print Service", и
программно самим агентом (см. "Проверено локально" ниже).

**Принтер этикеток, который должен встать на замену** (Xprinter
XP-235B) — **только USB**, LAN у него нет вообще. Когда дойдёт очередь
до него: агент нужно будет переключить с сетевого сокета на печать
через Windows-драйвер принтера или прямой USB — сама очередь заданий,
расчёт срока годности и страница повара не поменяются, тронуть
придётся только функцию `sendToPrinter()` в `print-agent.js`. Также
не факт, что у него тот же набор команд (ESC/POS) — на наклейке
принтера это не было явно указано, надо проверить по факту.

### Кириллица на чеке — код страницы придётся подобрать по месту

ESC/POS-принтеры почти никогда не понимают UTF-8 напрямую — текст
кодируется в CP866 (таблица `CP866_MAP` в `print-agent.js`, вручную,
без внешних библиотек, проверена побайтово против стандарта CP866) и
принтеру заранее говорится, какую кодовую страницу использовать
(команда `ESC t n`). Но какой именно НОМЕР `n` соответствует CP866 —
зависит от прошивки конкретного принтера, узнать заранее нельзя.

Запустить `node print-agent.js --codepage-test` — распечатает одну и
ту же фразу под несколькими вероятными номерами (17, 18, 19, 6, 7, 34,
255) подряд. На бумаге найдёте строку, где кириллица читается нормально
— этот номер вписать в `CONFIG.CYRILLIC_CODEPAGE` наверху
`print-agent.js`.

### Настройка агента на моноблоке (Windows)

1. Поставить Node.js (с nodejs.org, LTS, пару кликов) — если ещё нет.
2. Скопировать `agent/print-agent.js` на моноблок, открыть текстовым
   редактором, поправить блок `CONFIG` наверху:
   - `BACKEND_URL` — адрес KitchenDesk (`https://kitchendesk.chefplan.ru`).
   - `AGENT_TOKEN` — тот же секрет, что вписали в `.env` как
     `OKO_SHELF_LIFE_AGENT_TOKEN` на сервере.
   - `PRINTER_IP` — IP принтера (тестовая печать с самого принтера).
   - `CYRILLIC_CODEPAGE` — см. выше, подобрать через `--codepage-test`.
   - `FEED_LINES_BEFORE_CUT` — сколько пустых строк оставлять перед
     обрезкой бумаги (по умолчанию 8, примерно 2-3 см при обычной высоте
     строки). Было 3 — на реальном принтере резало прямо по последней
     строке/QR-коду, неудобно было взять чек пальцами; если 8 окажется
     мало или много — можно поправить это число.
3. Запустить `node print-agent.js` в консоли — если видно
   `Агент печати KitchenDesk запущен...` без ошибок, всё подключилось.
4. Чтобы агент поднимался сам при каждом включении моноблока —
   `node print-agent.js --install-autostart`. Сам создаёт в папке
   автозагрузки Windows (`%APPDATA%\Microsoft\Windows\Start Menu\
   Programs\Startup`) файл `KitchenDeskPrintAgent.vbs`, который при
   входе в систему запускает агент **без видимого окна консоли** —
   через `WScript.Shell.Run(..., 0, False)`, стандартный способ на
   Windows запустить консольную программу полностью в фоне. Рядом со
   `print-agent.js` при этом появляются ещё два файла:
   `KitchenDeskPrintAgentLauncher.bat` (сам запуск `node print-agent.js`
   — на него ссылается `.vbs`) и копия `KitchenDeskPrintAgent.vbs`
   (можно дважды кликнуть по ней в любой момент, чтобы запустить агент
   прямо сейчас, тоже без окна, не дожидаясь перезагрузки). Руками
   искать `shell:startup` и делать ярлык не нужно. Путь внутри
   `.bat`/`.vbs` — та папка, откуда запущен `print-agent.js`
   (`__dirname`), так что скрипт должен лежать на постоянном месте
   (Рабочий стол и т.п.), не переноситься потом; при переносе нужно
   заново выполнить `--install-autostart`.
   Подтверждение, что агент вообще запустился, раз окна на экране не
   будет, — тестовый чек на принтере (см. ниже).
   Более ранняя версия клала видимый `.bat` прямо в папку автозагрузки
   под тем же именем — при повторном `--install-autostart` он находится
   и удаляется автоматически, чтобы агент не запускался дважды.

### Подтверждение запуска

При каждом старте агента (в том числе тихом — из автозагрузки, без
консоли на экране) на принтер сразу печатается короткий чек:

```
KitchenDesk
------------------------------
Агент печати запущен
20.09.2026 15:01
------------------------------
```

Это просто физическое доказательство "агент поднялся" — не нужно
гадать, ожил ли он после включения моноблока. Ошибка принтера в этот
момент (не включён, не в сети) не останавливает запуск агента —
опрос заданий стартует в любом случае, ошибка только пишется в
консоль.

### Что печатается на этикетке

```
KitchenDesk
------------------------------
ПФ Крем ОКО
Разморожено: 20.09.2026 15:01
Годен до: 21.09.2026 15:01
Кто: Марина
------------------------------
```

Если у позиции в справочнике `shelfLifeHours: null` (срок не
распознан) — вместо даты печатается «Годен до: _______________
(впишите)», чтобы повар дописал от руки, а не выдавал этикетку без
даты вообще.

**Дизайн чека собирается на сервере, не в агенте.** `store.
createPrintJob()` строит готовые строки текста (`job.printLines`) в
момент создания задания и кладёт их прямо в задание — агент
(`print-agent.js`) их не сочиняет, только кодирует в CP866 и шлёт
байты принтеру как есть (`buildLabel()` в агенте — просто
`job.printLines || [job.itemName]`). Так любая правка того, что и в
каком порядке печатается, — это правка `buildPrintLines()` в
`oko-shelf-life-store.js` и обычный деплой на сервер; файл на
моноблоке трогать не нужно вообще. Раньше (первая версия) текст
собирался прямо в `print-agent.js` — при любой правке дизайна
пришлось бы заново раздавать агента на моноблок.

## Проверено локально перед деплоем

Роутер и хранилище прогнаны на тестовом сервере (не на боевом), через
Playwright: вход по паролю, список всех 185 позиций рендерится
корректно, поиск по названию фильтрует верно (проверено на "ганаш" —
ровно 1 результат), добавление новой позиции с последующим удалением
(состояние справочника не засорилось), редактирование существующей
позиции (смена срока с "10 суток" на "48 часов" — колонка "Срок"
обновилась). Живая подсказка "Распознано: N ч." в форме добавления/
редактирования проверена и совпадает с тем, что реально сохраняется на
сервере. Импорт всех 185 позиций из присланного .xlsx прогнан дважды
(до и после фикса регулярки для "суток") — после фикса `shelfLifeHours`
распознан у всех 185 без исключений (проверено программно, не только
визуально).

**Очередь печати + агент** — прогнано полностью локально: поднят
настоящий бэкенд, фейковый TCP-сервер вместо принтера (порт 19100,
декодирует полученные байты ОБРАТНО из CP866 в текст для проверки) и
сам `print-agent.js` без изменений в логике, только адреса в конфиге
указывают на локальный тестовый стенд. Через Playwright: страница
повара показывает все 185 позиций, поиск фильтрует верно, создание
задания «Разморозил» для позиции со сроком 24 часа — подтверждение
показало верную дату (+24 часа), «Заморозил» для позиции со сроком
5 суток — верную дату (+120 часов). Агент забрал оба задания за
секунду опроса, фейковый принтер получил и корректно раскодировал
кириллицу (имя позиции, оба варианта действия, дата, кто) — побайтовая
проверка через CP866-таблицу в обе стороны (кодирование в агенте,
раскодирование в тестовом принтере, независимые копии таблицы). Оба
задания в `oko-shelf-life-print-jobs.json` перешли в статус `printed`
с `printedAt`. Отдельно проверены границы доступа: агентские роуты
(`/jobs/pending`, `/jobs/:id/done`) отдают 401 без токена и с неверным
токеном, 200 с верным; публичные роуты повара (`/items`, `POST /jobs`)
работают вообще без какой-либо авторизации, как и задумано. Утилита
`--codepage-test` проверена отдельно — печатает все 7 кандидатов
кодовых страниц с подписанными номерами, раскодировано верно на
фейковом принтере (сам подбор правильного номера на РЕАЛЬНОМ принтере
— уже на стороне пользователя, программно это не проверить).

**Подтверждение запуска** — прогнано на том же фейковом принтере:
обычный запуск `node print-agent.js` (без флагов) сразу, до первого
опроса заданий, шлёт короткий чек «Агент печати запущен» с датой и
временем — фейковый принтер получил и верно раскодировал кириллицу.
Ошибка соединения с принтером в этот момент поймана и залогирована
(`try/catch` вокруг печати подтверждения), опрос заданий по расписанию
всё равно стартовал следом — проверено, что один сбой печати
подтверждения не блокирует остальную работу агента.

**Автозагрузка без окна** — `--install-autostart` прогнан локально с
поддельной `APPDATA`: проверено, что создаются `.vbs` в папке
автозагрузки и рядом со скриптом, а также `.bat`-лаунчер рядом со
скриптом (сам `.bat` в автозагрузку больше не кладётся); содержимое
всех трёх файлов проверено построчно (правильные пути, правильная
команда `WshShell.Run` с флагом скрытого окна `0`). Отдельно проверена
подстраховка от задвоения: если в папке автозагрузки лежит старый
видимый `KitchenDeskPrintAgent.bat` (с более ранней версии агента) —
повторный `--install-autostart` находит и удаляет его автоматически,
проверено симуляцией такого файла перед запуском. Сам факт, что `.vbs`
реально запускает `node` без окна, — это поведение `WScript.Shell` на
самой Windows, программно на Linux-стенде не воспроизвести; это
единственная часть автозагрузки, проверенная только логически (по
документированному поведению `WshShell.Run(..., 0, False)`), не через
тестовый прогон.
