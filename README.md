# Жигули — калькуляции (ТТК)

> **«Жигули» — рабочее кодовое имя.** Ничего не значит, нужно только чтобы не путать
> с KitchenDesk. В интерфейсе продукт называется нейтрально — «Калькуляции».

Отдельный продукт для заведений, которым из KitchenDesk нужен только раздел
технологических карт: сайт-панель, а позже Telegram-бот и мини-апп на каждого клиента.

**Это самостоятельный проект, а не часть KitchenDesk.** Из KitchenDesk взята только
логика модуля ТТК как отправная точка (построчный состав брутто/нетто/% потерь,
полуфабрикаты, калькулятор пересчёта, выгрузка PDF/Excel, импорт из iiko). Код,
база, дизайн, процесс и деплой — свои. Правки в KitchenDesk сюда не переносятся
автоматически, и наоборот.

## Устройство

```

  src/db/migrations/    NNN_*.sql, применяются автоматически при старте
  src/middleware/auth.js  JWT, роли, изоляция клиентов (req.tenantId)
  src/services/         ВСЯ бизнес-логика — без Express, чтобы её же звал бот
    recipes.js          ТТК: список, карточка, сохранение состава, связи п/ф, пересчёт
    exports.js          PDF (pdfkit + DejaVu) и Excel (exceljs) — на сервере
    categories.js users.js tenants.js
  src/routes/           тонкие HTTP-обёртки над services
  scripts/create-platform-admin.js
web/                    Vite + React 19 + TypeScript + Tailwind 3 + TanStack Query
  src/pages/            Login, Recipes (список+карточка), RecipeEditor, Categories, Team, Platform, Account
  src/components/       RecipeDetail (калькулятор), ImportModal (разбор выгрузки iiko), Layout, ui
  src/lib/calc.ts       калькулятор пересчёта (дублирует серверный recipes.scale)
```

### Модель данных

- `tenants` — клиенты (заведения). `slug` — латинский идентификатор, для ссылки мини-аппа.
- `users` — у сотрудника всегда `tenant_id`; у администратора платформы `tenant_id IS NULL`,
  `is_platform_admin`. Роли: `owner` (всё + команда), `editor` (ведёт ТТК, выгружает),
  `viewer` (повар: смотрит и пересчитывает, без выгрузки и архива). `tg_id` заготовлен под бота.
- `categories`, `recipes`, `recipe_ingredients` — всё с `tenant_id` (у ингредиентов через рецепт).
- Полуфабрикат — `recipes.kind = 'semi'` (не префикс «ПФ» в названии, как в KitchenDesk).
  Строка состава связывается с ним по `linked_recipe_id`: явно из автоподсказки или сама —
  по точному совпадению названия. Когда карта становится полуфабрикатом, одноимённые строки
  других карт подвязываются автоматически. Циклы (A в B, B в A) запрещены на сервере.
- Из двух величин брутто / нетто / % потерь третья досчитывается (и на клиенте, и на сервере).

### Изоляция клиентов

Каждый запрос к данным идёт через `authenticate` → `req.tenantId`. Сотрудник всегда в своём
клиенте; администратор платформы выбирает клиента заголовком `X-Tenant-Id` (во фронтенде —
кнопка «Войти» на странице «Заведения»). Все функции в `services/` принимают `tenantId`
первым аргументом и фильтруют по нему каждый запрос — **новый код обязан делать так же**.
Пользователь перечитывается из БД на каждый запрос: отключение сотрудника или приостановка
заведения срабатывают сразу.

## Домен и nginx

`jigulibar.chefplan.ru` → A-запись на `5.129.238.76` (подключено 2026-09-24). nginx-конфиг
`/etc/nginx/sites-available/zhiguli` — простой `proxy_pass` на `127.0.0.1:3008` с
`X-Forwarded-For`/`X-Forwarded-Proto`, `client_max_body_size 10m` (фото до 8 МБ). HTTP → 301 на HTTPS.
`trust proxy` на loopback — лимит попыток входа считает реальные IP клиентов (проверено).
Вебхуки ботов (шаг 2) пойдут на этот же домен: `https://jigulibar.chefplan.ru/tg/<id>`.

## Что сделано (шаг 1 — сайт)

- Вход по логину/паролю, лимит 10 неудачных попыток за 15 минут с IP.
- Администратор платформы: список заведений, создание заведения вместе с владельцем
  (пароль показывается один раз), приостановка/включение, вход внутрь заведения.
- ТТК: список с поиском (по названию и ингредиентам), фильтры по категории и типу, архив;
  карточка с составом, технологией, КБЖУ, «входит в состав», фото.
- Калькулятор: множитель, на N порций, на нужный выход (кг/г, л/мл), от количества продукта.
  Выгрузка PDF/Excel идёт с тем же пересчётом (`?k=`).
- Редактор: построчный состав с автодосчётом, порядок строк, связь с п/ф, фото, выход, КБЖУ.
- Импорт каталога ТТК из выгрузки iiko (xlsx/xls/csv) с предпросмотром.
- Категории (порядок, переименование, удаление без потери ТТК), команда (роли, отключение,
  сброс пароля), смена своего пароля.

Проверено: API — 45 сценариев (роли, изоляция клиентов, досчёт, связи, циклы, выгрузка);
интерфейс — проход в Playwright на десктопе и телефоне за владельца, повара и администратора.

## Шаг 2 — боты клиентов (сделано 2026-09-24)

Бот подключается из панели без правки кода: «Заведения» → «Подключить бота» у заведения
(или сразу в форме нового заведения — поле «Telegram-бот»), вставить токен от @BotFather.

Что происходит при сохранении (`services/bots.js` → `connect`):
1. проверка формата и `getMe` — токен живой и это бот; тот же бот не может быть у двух заведений;
2. `setWebhook` на `https://jigulibar.chefplan.ru/tg/<id строки tenant_bots>` со случайным
   `secret_token` (64 hex), `allowed_updates: [message]`;
3. `setChatMenuButton` — кнопка «ТТК» в меню бота открывает мини-апп `…/tg-app?t=<slug>`;
4. если Telegram не дал настроить вебхук — ничего не сохраняется (при замене токена — откат к прежнему).

**Токен — секрет.** В БД только `token_encrypted` (AES-256-GCM, `utils/secretBox.js`), ключ
`BOT_TOKEN_KEY` в `server/.env`. API отдаёт только последние 4 символа. Ошибки Telegram
логируются без токена. **Потеря `BOT_TOKEN_KEY` = токены всех ботов придётся ввести заново**
(боты и данные не пострадают) — ключ стоит сохранить отдельно.

Вебхук (`routes/webhook.js`): неверный/отсутствующий `X-Telegram-Bot-Api-Secret-Token` → 401;
отвечаем 200 сразу, обрабатываем после. Отключённый бот молчит. Бот отвечает только в личке.

Мини-апп (`web/src/pages/TgApp.tsx`): заведение берётся из `?t=<slug>` (кнопка бота) или
`start_param` (ссылка `t.me/<бот>?startapp=<slug>`, если у бота включён Main Mini App).
`POST /api/auth/telegram {initData, tenant}` — подпись `initData` проверяется токеном бота
ИМЕННО этого заведения (initData другого бота не пройдёт), свежесть — 24 ч.

Привязка сотрудника: «Команда» → «В Telegram» → одноразовая ссылка
`t.me/<бот>?start=link_<код>` (24 ч, новая отменяет старую, работает только в боте своего
заведения). Сотрудник жмёт «Старт» → `users.tg_id` привязан. Отвязать — там же.

Отключение: `deleteWebhook` + кнопка меню по умолчанию + `is_active=false`; токен и привязки
сохраняются, «Включить» настраивает всё заново. «Удалить» — то же + стирает токен.
Статус в панели сверяется с `getWebhookInfo` (вебхук наш? ошибки доставки?).

Проверено: 45 API-сценариев на фейковом Bot API (отдельный экземпляр сервера с
`TELEGRAM_API_BASE`), проход в Playwright (подключение, приглашение, привязка, вход в мини-апп
с подписанным initData, отказ непривязанному и вне Telegram). Живым ботом ещё не проверялось.

Известное ограничение: скачивание PDF/Excel изнутри мини-аппа (webview Telegram) может не
сработать — выгрузку лучше делать с сайта. Повару выгрузка и так закрыта.
