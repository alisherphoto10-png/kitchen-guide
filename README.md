# Жигули — калькуляции (ТТК)

> **«Жигули» — рабочее кодовое имя.** Ничего не значит, нужно только чтобы не путать
> с KitchenDesk. В интерфейсе продукт называется нейтрально — «Калькуляции».

Отдельный продукт для заведений, которым из KitchenDesk нужен только раздел
технологических карт: сайт-панель, а позже Telegram-бот и мини-апп на каждого клиента.

**Это самостоятельный проект, а не часть KitchenDesk.** Из KitchenDesk взята только
логика модуля ТТК как отправная точка (построчный состав брутто/нетто/% потерь,
полуфабрикаты, калькулятор пересчёта, выгрузка PDF/Excel, импорт из iiko). Код,
база, дизайн, процесс и деплой — свои. Правки в KitchenDesk сюда не переносятся
автоматически, и наоборот.

### Модель данных

- `tenants` — клиенты (заведения). `slug` — латинский идентификатор, для ссылки мини-аппа.
- `users` — у сотрудника всегда `tenant_id`; у администратора платформы `tenant_id IS NULL`,
  `is_platform_admin`. Роли: `owner` (владелец: всё + команда;
  владельцев у заведения может быть несколько — назначаются в «Команде»), `viewer` (повар: смотрит и
  пересчитывает, без выгрузки и архива). Роль «технолог» (`editor`) убрана 2026-09-24 (миграция 006,
  бывшие технологи стали владельцами). `tg_id` заготовлен под бота.
- `categories`, `recipes`, `recipe_ingredients` — всё с `tenant_id` (у ингредиентов через рецепт).
- Полуфабрикат — `recipes.kind = 'semi'` (не префикс «ПФ» в названии, как в KitchenDesk).
  Строка состава связывается с ним по `linked_recipe_id`: явно из автоподсказки или сама —
  по точному совпадению названия. Когда карта становится полуфабрикатом, одноимённые строки
  других карт подвязываются автоматически. Циклы (A в B, B в A) запрещены на сервере.
- Из двух величин брутто / нетто / % потерь третья досчитывается (и на клиенте, и на сервере).

### Изоляция клиентов

Каждый запрос к данным идёт через `authenticate` → `req.tenantId`. Сотрудник всегда в своём
клиенте; администратор платформы выбирает клиента заголовком `X-Tenant-Id` (во фронтенде —
кнопка «Войти» на странице «Заведения»). Все функции в `services/` принимают `tenantId`
первым аргументом и фильтруют по нему каждый запрос — **новый код обязан делать так же**.
Пользователь перечитывается из БД на каждый запрос: отключение сотрудника или приостановка
заведения срабатывают сразу.

## Домен и nginx

`jigulibar.chefplan.ru` → A-запись на `5.129.238.76` (подключено 2026-09-24). nginx-конфиг
`/etc/nginx/sites-available/zhiguli` — простой `proxy_pass` на `127.0.0.1:3008` с
`X-Forwarded-For`/`X-Forwarded-Proto`, `client_max_body_size 10m` (фото до 8 МБ). HTTP → 301 на HTTPS.
`trust proxy` на loopback — лимит попыток входа считает реальные IP клиентов (проверено).
Вебхуки ботов (шаг 2) идут на этот же домен: `<PUBLIC_BASE_URL>/tg/<id>`.

**Смена домена 2026-09-24: `jigulibar.chefplan.ru` → `calc.chefplan.ru`.** Новый конфиг
`/etc/nginx/sites-available/calc` (такой же `proxy_pass`, свой сертификат certbot, HTTP → 301 на HTTPS),
`PUBLIC_BASE_URL=https://calc.chefplan.ru` в `server/.env` (копия прежнего — `.env.bak-20260924-calc`).
Адрес сайта в коде нигде не зашит — вебхуки, кнопка мини-аппа и ссылка гида по умолчанию строятся из
`PUBLIC_BASE_URL`, но **уже подключённые боты держат старый адрес, пока их не перенастроить**
(«Заведения» → бот → «Отключить» → «Включить» или заново токен — `configureTelegram` ставит новый вебхук
и кнопку). Поэтому старый домен оставлен рабочим (не редиректом: Telegram не идёт по редиректу вебхука).
Когда все боты и ссылка гида переедут — старый `sites-available/zhiguli` можно заменить на 301 на новый домен.
Входы на сайте привязаны к домену (localStorage) — на новом адресе нужно войти заново.

## Что сделано (шаг 1 — сайт)

- Вход по логину/паролю, лимит 10 неудачных попыток за 15 минут с IP.
- Администратор платформы: список заведений, создание заведения вместе с владельцем
  (пароль показывается один раз), приостановка/включение, вход внутрь заведения.
- ТТК: список с поиском (по названию и ингредиентам), фильтры по категории и типу, архив;
  карточка с составом, технологией, КБЖУ, «входит в состав», фото.
- Калькулятор: множитель, на N порций, на нужный выход (кг/г, л/мл), от количества продукта.
  Выгрузка PDF/Excel идёт с тем же пересчётом (`?k=`).
- Редактор: построчный состав с автодосчётом, порядок строк, связь с п/ф, фото, выход, КБЖУ.
- Импорт каталога ТТК из выгрузки iiko (xlsx/xls/csv) с предпросмотром.
- Категории (порядок, переименование, удаление без потери ТТК), команда (роли, отключение,
  сброс пароля), смена своего пароля.

Проверено: API — 45 сценариев (роли, изоляция клиентов, досчёт, связи, циклы, выгрузка);
интерфейс — проход в Playwright на десктопе и телефоне за владельца, повара и администратора.

## Шаг 2 — боты клиентов (сделано 2026-09-24)

Бот подключается из панели без правки кода: «Заведения» → «Подключить бота» у заведения
(или сразу в форме нового заведения — поле «Telegram-бот»), вставить токен от @BotFather.

Что происходит при сохранении (`services/bots.js` → `connect`):
1. проверка формата и `getMe` — токен живой и это бот; тот же бот не может быть у двух заведений;
2. `setWebhook` на `https://jigulibar.chefplan.ru/tg/<id строки tenant_bots>` со случайным
   `secret_token` (64 hex), `allowed_updates: [message]`;
3. `setChatMenuButton` — кнопка «ТТК» в меню бота открывает мини-апп `…/tg-app?t=<slug>`;
4. если Telegram не дал настроить вебхук — ничего не сохраняется (при замене токена — откат к прежнему).

**Токен — секрет.** В БД только `token_encrypted` (AES-256-GCM, `utils/secretBox.js`), ключ
`BOT_TOKEN_KEY` в `server/.env`. API отдаёт только последние 4 символа. Ошибки Telegram
логируются без токена. **Потеря `BOT_TOKEN_KEY` = токены всех ботов придётся ввести заново**
(боты и данные не пострадают) — ключ стоит сохранить отдельно.

Вебхук (`routes/webhook.js`): неверный/отсутствующий `X-Telegram-Bot-Api-Secret-Token` → 401;
отвечаем 200 сразу, обрабатываем после. Отключённый бот молчит. Бот отвечает только в личке.

Мини-апп (`web/src/pages/TgApp.tsx`): заведение берётся из `?t=<slug>` (кнопка бота) или
`start_param` (ссылка `t.me/<бот>?startapp=<slug>`, если у бота включён Main Mini App).
`POST /api/auth/telegram {initData, tenant}` — подпись `initData` проверяется токеном бота
ИМЕННО этого заведения (initData другого бота не пройдёт), свежесть — 24 ч.

Привязка сотрудника (с 2026-09-24 — по логину/паролю, персональные ссылки убраны):
- владелец в «Команде» при добавлении сам задаёт логин и пароль (или генерирует);
- у бота одна общая ссылка `t.me/<бот>` — её показывает «Команда», можно кинуть в общий чат;
- непривязанному Telegram бот предлагает войти: логин → пароль (сообщение с паролем бот
  сразу удаляет из чата, `/cancel` — начать заново, незаконченный диалог живёт 10 мин);
- совпадение ищется только среди сотрудников этого заведения; при успехе `users.tg_id`
  записывается навсегда (`UPDATE … WHERE tg_id IS NULL` — два Telegram не займут одну запись),
  дальше бот и мини-апп пускают без пароля;
- неверные данные → «неверный логин или пароль» (одинаково для «нет логина» и «не тот пароль»,
  bcrypt гоняется по пустышке); сотрудник уже привязан к другому Telegram → отказ, перепривязать
  может только владелец кнопкой «сбросить» в «Команде»; привязанный Telegram сам сменить
  сотрудника не может;
- 5 неверных попыток подряд → этот Telegram заблокирован на 15 минут (`tg_auth_sessions`);
- бот работает только в личке, в группах молчит.
Логика: `services/telegramLink.js` (tryLink), диалог — `services/botUpdates.js`.

Отключение: `deleteWebhook` + кнопка меню по умолчанию + `is_active=false`; токен и привязки
сохраняются, «Включить» настраивает всё заново. «Удалить» — то же + стирает токен.
Статус в панели сверяется с `getWebhookInfo` (вебхук наш? ошибки доставки?).

Проверено: 45 API-сценариев + 29 сценариев входа по логину/паролю на фейковом Bot API (отдельный экземпляр сервера с
`TELEGRAM_API_BASE`), проход в Playwright (подключение, «Команда», вход в мини-апп
с подписанным initData, отказ непривязанному и вне Telegram). Живым ботом ещё не проверялось.

Известное ограничение: скачивание PDF/Excel изнутри мини-аппа (webview Telegram) может не
сработать — выгрузку лучше делать с сайта. Повару выгрузка и так закрыта.

## Шаг 3 — профиль мини-аппа, платные модули, техподдержка (сделано 2026-09-24)

### Профиль в мини-аппе
Сессия помнит, как открыта (`via` в JWT: `password` — сайт, `telegram` — мини-апп). В мини-аппе
в профиле нет «Сменить пароль» и «Выйти»; есть «Техподдержка» и «История обращений». Назад с
профиля — ссылка «К ТТК», логотип в шапке и системная кнопка «Назад» Telegram (`lib/telegram.ts`).

### Платные модули заведения
Реестр — `server/src/modules.js` (сейчас один: `recalc` — «Пересчёт»), включения — таблица
`tenant_modules` (нет строки = по умолчанию из реестра; платные выключены). Переключает
администратор платформы: «Заведения» → «Модули». Выключенный модуль виден, но заблокирован с
текстом «Доступно в расширенном тарифе — обратитесь к администратору»; API отвечает 403
`code: module_locked` (выгрузка с `?k≠1`). Базовые ТТК модули не затрагивают.
Новый модуль = запись в реестре + `requireModule('<key>')` на сервере + `useModule('<key>')` во фронтенде.

### Техподдержка (тикеты)
Сценарий: «Техподдержка» в профиле мини-аппа (или `/support` в боте) → мини-апп закрывается,
бот пишет «Напишите своё обращение» → следующее сообщение (в течение 24 ч) создаёт тикет →
пока тикет открыт, всё, что сотрудник пишет боту, добавляется в него (бот ставит реакцию 👌,
без лишних ответов) → администратор платформы отвечает на сайте («Поддержка»), ответ уходит в
тот же чат ботом заведения → закрывает тикет вручную (сотруднику приходит «закрыто») →
следующий вопрос — новый тикет. Историю всех своих обращений сотрудник видит в мини-аппе.
Владельцу заведения история не показывается (решение пользователя).

- Таблицы: `support_tickets` (одно открытое на сотрудника — уникальный индекс),
  `support_messages`, `users.support_requested_at`, `platform_settings`.
- Логика — `services/support.js`, вызывается из `botUpdates.js` для привязанных сотрудников.
- Ответ сохраняется, только если Telegram его принял (бот отключён / сотрудник заблокировал бота →
  ошибка в интерфейсе, текст остаётся в поле). Закрыть можно всегда.
- Только текст: фото без подписи → просьба описать словами; подпись к фото сохраняется.
- Команды `/start` и прочие в переписку не попадают.

Уведомления о новых тикетах и сообщениях (`services/supportNotify.js`): **отдельный бот платформы**
(не бот заведения — ему нужен `getUpdates`, а значит без вебхука). «Поддержка» → «Уведомления»:
токен бота → добавить бота в группу → в нужной теме `/start@бот` → «Найти чаты» → выбрать (туда
уходит пробное сообщение). В уведомлении кнопка «Открыть обращение» → `…/support/<id>`.
Сбой уведомления не мешает переписке, ошибка видна в окне настроек.

Проверено: 67 API-сценариев на фейковом Bot API (создание, продолжение, ответ, закрытие, новый
тикет, изоляция сотрудников и заведений, права, сбои доставки, устаревший запрос, группа/тема
уведомлений) + Playwright (мини-апп: профиль, закрытие по «Техподдержке», история, кнопка «Назад»;
админ: инбокс на десктопе и телефоне, ответ, закрытие/открытие, настройка уведомлений).
**Живым ботом не проверено.** Бот уведомлений ещё не создан — нужен токен от пользователя.

## Шаг 4 — экспорт в чат, бренд на документах, свой пароль, одна карточка тикета (2026-09-24)

- **Экспорт по каналу запроса.** Сайт — обычное скачивание (`GET /api/recipes/:id/export.pdf|xlsx`),
  без изменений. Мини-апп (сессия `via=telegram`) — `POST …/export.pdf|xlsx/telegram`: файл уходит
  документом (`sendDocument`) в личный чат сотрудника с ботом заведения, подпись — название ТТК
  (и «пересчитано ×k»). В меню мини-аппа пункты называются «Отправить в чат PDF/Excel».
  Отправка сотрудникам ботом заведения — `services/botDelivery.js` (им же пользуется техподдержка).
- **Бренд на документах:** «Калькуляции — модуль KitchenDesk» — мелко слева в подвале каждой
  страницы PDF; в Excel — последней строкой листа и в колонтитуле при печати. Интерфейс без бренда.
- **Свой пароль сотруднику:** «Команда» → «Пароль» — вписать свой (от 6 символов, можно одни
  цифры) или сгенерировать кубиком. `POST /api/team/:id/reset-password {password?}`.
- **Уведомление о тикете — одно сообщение на тикет** (`support_tickets.notify_chat_id/notify_message_id`,
  миграция 007). Создание тикета — `sendMessage`, дальше `editMessageText`: статус сверху
  (🟠 ждёт ответа / 🔵 отвечено / ✅ ЗАКРЫТО), ниже переписка (последние сообщения, если не влезает).
  Карточку удалили в группе или сменили чат уведомлений — появится новая. Обновления одного
  тикета идут по очереди (две быстрые реплики не дают двух карточек).
  **Учтите:** правка сообщения в Telegram не даёт звука/пуша — о новой реплике в уже открытом
  тикете группа узнаёт только по изменившейся карточке.

Проверено: 30 API-сценариев на фейковом Bot API (выгрузка, sendDocument, права, модуль, сбои
доставки; пароль; карточка: создание, правка, ответ, закрытие, повторное открытие, удалённая
карточка, гонка, длинная переписка) + Playwright (окно пароля, меню экспорта на сайте и в мини-аппе).

## Шаг 7 — интеграция с iiko, платный модуль `iiko` (2026-09-25)

Задача — `print-agent/README.md` ветки `claude/oko-waiter-guide-xlsx` (коммиты `a14a87d`, `54b2767`).

- **Модуль** `iiko` в `MODULES` (`server/src/modules.js`), по умолчанию выключен; включает/выключает
  администратор платформы в «Модулях» заведения. Все `/api/iiko/*` — `requireRole('owner')` +
  `requireModule('iiko')`: повару 403, выключенный модуль — 403 `module_locked` с `LOCKED_MESSAGE`.
- **Подключение — своё у заведения**, заводит владелец (не платформа): таблица `tenant_iiko` (миграция 009),
  пароль — `secretBox` (тот же ключ `BOT_TOKEN_KEY`, что у токенов ботов), наружу не отдаётся.
  `GET /api/iiko` (или `null`), `PUT /api/iiko {base_url, login, password}` — сохраняет только если iiko пустил
  (пустой пароль при правке = оставить прежний), `POST /api/iiko/test` (404 без подключения),
  `DELETE /api/iiko`, `POST /api/iiko/import`.
- **Клиент** — `services/iikoApi.js`: `GET /resto/api/auth?login=&pass=<SHA1>`, токен → `key=`;
  `assemblyCharts/getAll`, `entities/products/list`, `entities/list?rootType=MeasureUnit`; после работы всегда
  `logout` (токен занимает лицензию iiko). Адрес нормализуется к `https://<хост>/resto`. TLS с обычной проверкой
  сертификата; только `https` и только публичные адреса (запрос делает наш сервер — защита от походов во
  внутреннюю сеть). `IIKO_ALLOW_LOCAL=1` снимает оба ограничения — **только для тестового экземпляра с фейковым iiko**.
- **Актуальная версия карты** — из неистёкших (`dateTo` нет или в будущем) с самым поздним `dateFrom`
  (не требуем `dateFrom <= сегодня` — на демо KitchenDesk так выбиралась пустышка).
- **Импорт** (`services/iiko.js`, одна транзакция + advisory lock на заведение):
  `products.type === 'PREPARED'` → `kind='semi'`, иначе `'dish'`; брутто = нетто = `amountIn`, потери 0;
  единица строки — `mainUnit` продукта по справочнику; выход: `mainUnit` кг/л → `yield_weight`/`yield_unit`,
  шт/порц → `yield_count` (`assembledAmount`). Удалённые в iiko и нерезолвящиеся продукты пропускаются и
  перечисляются в сводке. Карта ищется по `recipes.iiko_product_id`; если её ещё нет — берётся **ручная карта с
  тем же названием** (без iiko-метки), чтобы не было двух одинаковых; иначе создаётся новая. Технологию, фото,
  категорию, примечание, КБЖУ импорт не трогает. Связи п/ф: строка, которая сама импортированный ПФ, → его карта;
  иначе — точное название существующего ПФ (как при ручном вводе); плюс ручные карты с таким названием в составе
  подвязываются к импортированному ПФ (`linkExistingRows`). Сводка: новые / обновлённые (реально изменившиеся) /
  без изменений / пропущенные — с именами; последняя хранится в `tenant_iiko.last_import_result`.
- **Блокировка**: `recipes.iiko_managed_at`. Пока модуль включён (`iiko_locked` в карточке), `PUT /api/recipes/:id`
  молча оставляет прежними название, тип, выход и состав (закрывает и прямой запрос в обход UI). **Модуль выключили —
  карты, метка и связи остаются, но карта снова правится руками** (синхронизации нет — иначе карта застыла бы
  навсегда); включат обратно — повторный импорт перезапишет. Удаление подключения карт не трогает.
- **Интерфейс**: кнопка «iiko» рядом с «Импорт» на странице ТТК (владелец) → окно `IikoModal` (при выключенном
  модуле — описание и `MODULE_LOCKED_TEXT`); метка «iiko» в списке, «из iiko · дата» в карточке; в редакторе
  заблокированные поля неактивны с пояснением. Гид, раздел 04 — одно предложение про прямое подключение.

Проверено: 49 API-сценариев на фейковом iiko (экземпляр `:3018` с `IIKO_ALLOW_LOCAL=1`, заведение `smoke-*`,
удалено) — модуль выкл/вкл, 403 повару, 404 без подключения, неверный пароль не сохраняется, выбор версии
карты, ПФ и связи, повтор без дублей, изменение в iiko → «обновлено», прямой PUT не меняет состав, ошибка прав
iiko → 502 с понятным текстом, выключение модуля не удаляет данные, все сессии iiko закрыты. Защита адреса
(localhost/10.x/::1/http) — отдельно. **Живой прогон** против демо-стенда iiko KitchenDesk через API: 3 карты,
«СЛИВОЧНО-ТВОРОЖНЫЙ КРЕМ» → полуфабрикат, брутто = нетто, потери 0 % (как на скриншотах KitchenDesk), повтор —
0 новых / 3 без изменений. Playwright: окно подключения, импорт, карточка, заблокированный редактор.
