# Часть 1 — подключить существующий калькулятор банкетов и стресс-тест на реальных данных

По итогам Части 0: калькулятор банкетов **уже в основном написан**
(`backend/src/api/banquet.js`, таблицы `banquets`/`banquet_items`, роуты,
`Banquet.tsx`), просто не подключён к роутингу. Задача этой части — не
писать заново, а **проверить, действительно ли работает то, что уже есть**,
и подключить.

Состав ТТК — свободный текст без единого формата (см. отчёт Части 0), а
существующий парсер угадывает по regex/`LIKE`-поиску. Это может тихо
ошибаться. Цель — не поверить коду на слово, а **измерить**, насколько он
надёжен на реальных данных, и только потом решать, готов ли он к реальному
использованию.

## Шаг 1 — стресс-тест парсинга (сделать первым, ничего ещё не подключать)

Прогнать `banquet.js`-парсер (или скопировать его логику в отдельный
скрипт для теста, не трогая роутинг) **по всем реальным ТТК** в системе, не
только по нескольким примерам:

- Для каждого блюда — сколько строк состава успешно распозналось
  (`название — число единица`), сколько нет.
- Для каждой найденной ссылки на ПФ (по префиксу «пф»/«п/ф») — успешно ли
  `LIKE`-поиск нашёл соответствующий ттк, или нет.
- Для скольких блюд `yield` пустой или не парсится `parseFloat`-ом
  (влияет на пересчёт порций).

**Результат — конкретные числа**, не «вроде работает»: например «из N
ручных блюд успешно разобрано M, не разобрано K (список id/названий)»,
«из P ссылок на ПФ найдено Q, не найдено R (список)».

## Шаг 2 — решить, что делать с найденными проблемами

По итогам шага 1, для каждого класса проблем:

- **Строка не распозналась regex'ом** — не пропускать молча из расчёта.
  Показывать пользователю банкет-калькулятора явно: «не удалось разобрать:
  „…“» — по этому конкретному блюду/строке, чтобы человек знал, что сумма
  может быть неполной, а не считал тихо заниженное число за точное.
- **ПФ не нашёлся по имени** — то же самое: явно показать «не найден
  полуфабрикат „…“» вместо того, чтобы тихо посчитать его как обычный
  ингредиент (весом «1 pcs» условной единицы ПФ вместо раскрытого состава)
  или пропустить.
- **`yield` не парсится/пуст** — блюдо помечать как «пересчёт на порции
  недоступен», не выдавать посчитанное число как надёжное.

Не обязательно чинить сам парсинг (regex можно улучшить отдельно, если
после первого прохода окажется, что практических случаев мало) — но
**обязательно не выдавать неправильные числа как будто они верные**.

## Шаг 3 — подключить

- Добавить роут для `Banquet.tsx` **вне основной навигации/сайдбара** — по
  прямой ссылке, как и просили (по аналогии с тем, как `oko-order` живёт
  отдельно от общей структуры). Уточнить у пользователя точный путь/URL,
  если не очевиден из уже существующего кода компонента.
- Убедиться, что бэкенд-роуты (`GET/POST /api/banquets` и т.д.) реально
  подключены и работают за актуальной авторизацией (какой ролью должен
  быть доступен конструктор банкета — уточнить, если из кода не ясно).

## Шаг 4 — живой тест на реальном банкете

Создать один тестовый банкет на нескольких реальных блюдах с разным
числом порций, **обязательно включая `id=210` («ПФ чечевичный суп»)** —
блюдо с вложенными ссылками на другие ПФ (`id=157`, `id=958`), чтобы
проверить именно рекурсивное раскрытие. Вручную (на бумаге/в уме) посчитать
ожидаемый итог по паре ингредиентов и сверить с тем, что выдал калькулятор.
